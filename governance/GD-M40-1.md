## Decision 1 — Scope Boundary and Milestone Classification

M40 authorizes the first narrowly bounded live recruiting integration with
the dormant M38 Decision Case and Approval Foundation. M40 must: resolve
the existing final-offer and hire authorization inconsistency; establish
routine Tier 2 maker-checker approval; connect only the governed
recruiting workflow to M38; preserve `RolesGuard` as the live

remain deterministic and human-driven throughout. M40 must not activate
the broader M38 system for arbitrary business domains — every structural
non-reachability guarantee `GD-M38-1` Decision 19 established for every
domain OTHER than the recruiting offer/hire path remains fully in force
after M40 (Decision 19 below). **M40 governance completion does not mean
M40 implementation is complete or started** — this document authorizes a
future, separately instructed implementation task; it is not that task.

## Decision 6 — One-Packet Final-Offer-and-Hire Authorization Model

**One Tier 2 maker-checker authorization packet is used per final offer —
not two repetitive approval rounds.** The approved packet explicitly
authorizes both:

```text
1. Final approval and issuance of the governed offer terms
2. Later deterministic conversion of that accepted offer into a hire,
   provided all approved terms and governed source records remain valid
   and unchanged (Decision 14)
```

This satisfies the requirement that final offer and hire authorization
each receive maker-checker approval without forcing the same two humans
to approve materially identical information twice. `GD-M35-1` Decision 12
names both "routine final offer authorization" and "routine hire
authorization" as Tier 2 applications; this decision reads those as two
named applications of ONE bounded packet's authority, not two separate
packets, because the current code's own state machine already treats
offer-approval and hire as a single continuous, time-gapped decision about
the same terms for the same candidate and the same vacancy — never two
independent decisions.

The `DecisionCase` is **offer-subject-based**
(`subjectType: DecisionCaseSubjectType.OFFER`, `subjectId: offer.id`).
`decision-case-subject-resolver.ts` already validates this subject type
against a real, tenant-owned `Offer` row — no live schema constraint
requires a different existing M38 subject type.

The frozen evidence set (`EvidenceItem` rows, attached before submission
and frozen into the `ApprovalRequest` version via the existing
`ApprovalRequestEvidence` join) must reference, at minimum:

```text
- offer            (the Offer row itself)
- application      (the linked Application)
- candidate        (the Candidate the application is for)
- vacancy          (the Vacancy the offer is against)
- position         (the Position the vacancy is filling)
- department       (the Position's owning Department)
- approved compensation and proposed start date (the specific offer
  terms an approver is being asked to authorize)
- any other material offer term the live Offer record carries at
  submission time
```

Every `EvidenceItem` is a **reference** (`sourceType`/`sourceId`) to the
existing governed record, per the established M38 pattern — never a copy
of the underlying row. **Candidate or employee PII must never be copied
into generic JSON or audit metadata** — compensation, name, contact
information, and any other PII-bearing field are retrieved by the viewer
through the existing, already-tenant-scoped and RBAC-gated record lookup,
not duplicated into `EvidenceItem.metadata` or any `AuditEvent.metadata`
field (Decision 23).

## Decision 7 — Two-Authority Maker-Checker Rules

Every routine packet requires exactly:

```text
- one DEPARTMENT_OR_HIRING_AUTHORITY
- one HR_AUTHORITY
```

Temporary legacy-role qualification remains exactly as
`authority-category-mapping.ts` already implements it, unmodified:

```text
Hiring Manager -> DEPARTMENT_OR_HIRING_AUTHORITY
HR Director    -> HR_AUTHORITY
```

Binding rules, all already enforced at the database and service layer by
the existing `ApprovalService`/`authority-category-mapping.ts`
combination and reused unmodified by this decision:

```text
- The two approvals must come from two distinct human user IDs
  (idx_approval_decisions_request_decider unique index)
- One user may never satisfy both requirements, even if assigned both
  roles (assertHumanActorQualifiesForCategory checks the category
  against the requirement, not against the user's full role set; the
  distinct-decider index is category-agnostic and blocks a second
  decision by the same user on the same request regardless of which
  requirement they attempt)
- The preparer (decisionCase.preparedByUserId) may satisfy at most one
  requirement (PreparerSeparationViolation, enforced today only for Tier
  1/Tier 3; this decision additionally requires this same preparer check
  be evaluated for Tier 2 requirements at implementation time — see
  Decision 28, Validation Gate)
- Candidate acceptance (recordOfferResponse()) does not count as a human
  approval of any Tier 2 requirement -- it remains, unchanged, the
  candidate's own separate action against a SENT offer (Decision 12)
- System Administrator does not qualify for either requirement -- SA is
  absent from DORMANT_ROLE_MAPPING's values today and must remain absent
- Compliance Officer is not part of routine maker-checker approval --
  Compliance Officer is never assigned to a Tier 2 requirement
- Independent Oversight Reviewer approval is not required for an ordinary
  offer or hire -- Tier 3 is added to a packet only when an existing,
  already-recorded DecisionCaseRiskTrigger is pending inclusion, never by
  default (Decision 16)
```

```text
- Recruiter
- Hiring Manager
- HR Director
```

**System Administrator must not gain preparation authority merely because
the user is an administrator** — SA is deliberately absent from this
list. This decision does not use M40 to redesign every legacy
offer-creation permission: `offers:create` and `offers:update`'s existing
role mappings (`ROLES_SA_HRD_REC`, unchanged since M18) are explicitly
**out of scope** — intentional authorization changes are limited to the
final-offer-submission (`offers:submit`), approval (`offers:approve`),
issuance (`offers:issue`), and hire-execution (`hire:authorize`) path
necessary to resolve M40 (Decision 18).

## Decision 9 — System Administrator Exclusion; Elevation Deferral

**All System-Administrator-via-elevation substitution is deferred.** M40
must:

```text
- Remove System Administrator from routine final-offer approval
  (offers:approve role mapping loses System Administrator)
- Remove System Administrator from routine offer issuance where it would
  bypass the approved maker-checker path (offers:issue role mapping
  loses System Administrator)
- Remove System Administrator from routine hire execution
  (hire:authorize role mapping loses System Administrator)
- Prevent System Administrator from serving as either Tier 2 approver
  (already enforced by authority-category-mapping.ts's dormant mapping,
  unmodified)
- Avoid granting routine decision-case access merely because a user is an
  administrator (System Administrator receives no new read visibility
  into DecisionCase/ApprovalRequest/EvidenceItem records under this
  decision)
- Preserve technical administration separately from recruiting authority
  -- System Administrator's non-recruiting capabilities (user
  management, role assignment, audit recovery, and every capability
  unrelated to the final-offer/hire path) are entirely unaffected by
  this decision
```

**No emergency override is implemented.** `M35-COMMAND-CENTER-BLUEPRINT.md`
Section 13 floats an SA-via-elevation substitution for HR authority in a
hire case; that substitution is explicitly **not authorized by this
decision**. `GD-M37-1` elevation remains authorization-inert (Decision
21's three-part activation gate is unaffected and unadvanced by this
decision) — building a live dependency on an inert mechanism would either
silently grant nothing or require activating M37 outside this decision's
charter. **Any future elevation-based substitution requires its own
separate governance decision, made only after authorization-effective
elevation is explicitly approved** by that future decision — not assumed,
inherited, or partially credited by this one.

## Decision 10 — Offer Submission and Approval Lifecycle

```text
1. A final offer is prepared (existing createOffer()/updateOffer(), DRAFT
   status, unchanged).
2. Submission (POST /offers/:id/submit, offers:submit, now scoped to
   Recruiter/Hiring Manager/HR Director per Decision 8) transitions
   Offer.status DRAFT -> PENDING_APPROVAL (existing transition,
   unchanged) AND creates or retrieves the server-governed DecisionCase
   (subjectType: OFFER, subjectId: offer.id, a server-derived stable
   idempotency key per Decision 20 -- never a client-supplied key).
3. The same submission call invokes
   ApprovalService.submitApprovalRequest({basePlanType: 'TIER_2'}),
   creating a versioned Tier 2 ApprovalRequest with the two required
   ApprovalRequirement rows.
4. Evidence is frozen for that request version via the existing
   ApprovalRequestEvidence join (Decision 6's minimum evidence list).
5. Hiring Manager and HR Director each act on their own requirement via
   POST /offers/:offerId/approval-requirements/:requirementId/decision
   (Decision 17), which calls ApprovalService.recordApprovalDecision()
   unmodified. The first (non-completing) decision leaves Offer.status
   unchanged at PENDING_APPROVAL (Decision 15).
6. When both requirements reach GRANTED, ApprovalService's existing
   fail-fast resolution transitions the ApprovalRequest to APPROVED and
   the DecisionCase to APPROVED. In the SAME transaction, the governed
   final-offer submission service additionally transitions
   Offer.status PENDING_APPROVAL -> APPROVED, because this transition
   records completion of the approved decision, not a separate business
   action (Decision 22, Transaction 1).
```

Approval completion **must not**: send the offer, record candidate
acceptance, invoke the hire transaction, or create an employee. Those
remain separate, explicit, deterministic actions (Decisions 11-13).

## Decision 11 — Offer Issuance Lifecycle

The offer is **not** sent automatically on approval. `POST
/offers/:id/send` (`offers:issue`, now scoped to HR Director only per
Decision 9) remains a separate, explicit action. At implementation time,
`sendOffer()`'s existing precondition (`existing.status !== 'APPROVED'` ->
`OFFER_NOT_APPROVED`) must be extended to additionally re-verify, inside
the same transaction, that the offer's `ApprovalRequest` is still
`APPROVED` and not `SUPERSEDED` (Decision 14) before transitioning
`Offer.status` `APPROVED -> SENT` (Decision 22, Transaction 2).

## Decision 12 — Candidate-Response Boundary

The candidate's response continues to be recorded through the existing,
unmodified `recordOfferResponse()` process (`POST
/offers/:id/record-response`, `offers:record-response`, role mapping
unchanged). Acceptance transitions `Offer.status` `SENT -> ACCEPTED` and
sets `acceptedAt` exactly as today. **Acceptance does not automatically
create an employee** — `recordOfferResponse()`'s existing, explicit
guarantee that it never calls `prisma.application.update()` or
`prisma.employee.create()` is preserved unchanged. Candidate acceptance is
never treated as a human approval of any Tier 2 requirement (Decision 7).

## Decision 13 — Hire Execution Lifecycle and Server-Side Preconditions

An authorized HR user explicitly invokes the existing, application-scoped
`POST /applications/:id/hire` (`hire:authorize`, now scoped to HR
Director only per Decision 9). The hire action **revalidates and
consumes** the approved offer authorization — **knowing or submitting a
`decisionCaseId` must never be sufficient authorization; the server must
derive and validate every relationship itself.** Before executing, the
hire service must verify server-side, in addition to its existing
8-precondition chain (all preserved unweakened, per Decision 5's
reaffirmation of `GD-M19-1` Decisions 5-9):

```text
- same tenant (already enforced)
- application exists and remains eligible (already enforced)
- an accepted offer exists and is linked to this application (already
  enforced, Precondition 4)
- the linked offer has a completed Tier 2 maker-checker case (new)
- the current ApprovalRequest for that DecisionCase is APPROVED and not
  SUPERSEDED (new)
- both required authorities (DEPARTMENT_OR_HIRING_AUTHORITY,
  HR_AUTHORITY) show a GRANTED ApprovalDecision on that request (new --
  re-derived from the ApprovalRequirement/ApprovalDecision rows, never
  trusted from a cached or client-supplied flag)
- the two approving decidedByUserId values are distinct (new -- re-
  derived, not merely trusted from the database constraint's having
  prevented the alternative at write time)
- the approved offer terms have not materially changed since approval
  (new, Decision 14)
- offer status is ACCEPTED (already enforced via Precondition 4's
  ACCEPTED-offer lookup)
- application is not already hired (already enforced, Precondition 2,
  APPLICATION_ALREADY_HIRED)
- vacancy and position remain valid (already enforced, Preconditions
  6-8)
- no elevated-risk trigger blocks execution (new, Decision 16 --
  DecisionCaseRiskTrigger rows pending inclusion cause a fail-closed
  block, never a silent pass-through)
- the authorization has not already been consumed through a completed
  hire (already enforced by the existing APPLICATION_ALREADY_HIRED
  idempotency guard -- no new schema or constraint required, per
  Decision 20)
```

The existing hire mutation (`hire.service.ts`'s atomic 4-write
`$transaction`: employee creation, application transition to `HIRED`,
vacancy transition to `FILLED`, competing-application disposition, and
related position-assignment behavior) **must remain explicit,
deterministic, tenant-scoped, idempotent, transactional, and strictly
audited** (Decision 22, Transaction 3; Decision 23).

## Decision 14 — Material-Change Invalidation Rules; No Second Approval Round

**No second application-subject Tier 2 maker-checker case is created
after candidate acceptance** when: the same approved offer was accepted;
material terms remain unchanged; the application and vacancy remain
eligible; and no elevated-risk trigger exists. `POST
/applications/:id/hire` consumes the already-approved bounded
authorization from Decision 6 directly — it does not itself trigger any
new `DecisionCase` or `ApprovalRequest`.

A new approval **is** required only if:

```text
- compensation changes
- position changes
- department changes
- start date changes materially
- employment type or other governed offer term changes
- the approved request is superseded
- the offer is withdrawn, replaced, or reissued
- the application or vacancy no longer matches the approved evidence
- another governed invalidation condition applies
```

Any such change must invalidate the existing `ApprovalRequest` via M38's
existing supersession mechanism (`submitApprovalRequest()`'s existing
version-and-supersede path, already implemented and requiring no
modification) — never by silently keeping a stale approval valid.
Currently, `updateOffer()` only permits edits while `Offer.status ===
'DRAFT'`, i.e., before submission; if a future milestone relaxes that
constraint to allow post-approval edits, any such edit must call
supersession as part of that future change — this decision does not
itself relax `updateOffer()`'s DRAFT-only editability.

## Decision 15 — Binding Offer-Status Transition Table

This decision is **fully resolved by this governance document and is not
deferred to implementation-time design.** It was reconciled directly
against the live `offer.service.ts` (re-read in full for this
correction): `submitOffer()`, `approveOffer()`, `sendOffer()`,
`recordOfferResponse()`, `withdrawOffer()`, `updateOffer()`, and the
exact live `OFFER_TERMINAL_STATUSES = ['ACCEPTED', 'DECLINED',
'WITHDRAWN']` constant. **No new `Offer.status` value and no migration
are authorized or required** — every governed outcome below is
represented safely by the seven existing live values.

| Governed event | Offer.status before | Offer.status after | Live mechanism reused |
|---|---|---|---|
| Final-offer submission | `DRAFT` | `PENDING_APPROVAL` | `submitOffer()`, unmodified transition |
| First requirement GRANTED, second still open | `PENDING_APPROVAL` | `PENDING_APPROVAL` (unchanged) | No `Offer` write at all — `ApprovalService.recordApprovalDecision()` returns `SUCCESS_PENDING`; the governed submission service performs no `Offer.status` mutation on this outcome |
| Second (completing) requirement GRANTED | `PENDING_APPROVAL` | `APPROVED` | `approveOffer()`'s existing exact transition, now triggered by `ApprovalService`'s `SUCCESS_REQUEST_APPROVED` outcome inside the same transaction (Decision 22, Transaction 1) instead of a single caller |
| Needs Information | `PENDING_APPROVAL` | `DRAFT` | Reuses `DRAFT`, the live model's only editable state (`updateOffer()` already permits edits solely when `status === 'DRAFT'`) |
| Revision | `DRAFT` | `DRAFT` (unchanged) | Existing `updateOffer()`, DRAFT-only, unmodified |
| Resubmission | `DRAFT` | `PENDING_APPROVAL` | Existing `submitOffer()` transition, reused identically to initial submission; the **same** `DecisionCase` is reused (never a new case) and a **new** `ApprovalRequest` version is created with a newly frozen evidence set, exactly as `ApprovalService.submitApprovalRequest()` already implements for a `NEEDS_INFORMATION`-origin submission (`DECISION_CASE_RESUBMITTED` fires automatically); the prior request becomes `SUPERSEDED` |
| Rejection | `PENDING_APPROVAL` | `WITHDRAWN` | Reuses `WITHDRAWN`, the live model's only terminal "will not proceed" state — see the semantic justification below |
| Issuance | `APPROVED` | `SENT` | `sendOffer()`'s existing exact transition, extended with Decision 11's re-validation, unmodified otherwise |
| Candidate acceptance | `SENT` | `ACCEPTED` | `recordOfferResponse()`'s existing exact transition, unmodified |
| Candidate decline | `SENT` | `DECLINED` | `recordOfferResponse()`'s existing exact transition, unmodified |
| Withdrawal (any non-terminal status, human-initiated, independent of Tier 2 rejection) | any non-terminal | `WITHDRAWN` | `withdrawOffer()`'s existing, unmodified, already-status-agnostic transition — remains available as its own separate action under `offers:withdraw`, unchanged |
| Hire conversion | `ACCEPTED` (on the `Offer`); `Application.status` transitions `OFFER → HIRED` | `Offer.status` itself does not change on hire — `Application`/`Vacancy`/`Employee` transition per `GD-M19-1` Decisions 5-9, unmodified | `hire.service.ts`'s existing atomic transaction (Decision 13); requires `Offer.status === 'ACCEPTED'` and a completed, `APPROVED`, non-superseded Tier 2 packet; **adds no second approval round** |

**Why `WITHDRAWN` is the semantically correct rejection state, not a new
enum value:**

```text
1. WITHDRAWN already represents exactly one business fact: "this offer
   will not proceed to hiring" -- independent of WHY. A Tier 2 rejection
   and a voluntary human withdrawal are two different CAUSES of the
   identical business outcome, not two different outcomes. The live
   model already treats "cause" as something the audit trail records,
   not something Offer.status itself encodes -- withdrawOffer() today
   already collapses every possible withdrawal reason (candidate
   request, better candidate found, budget change, or anything else)
   into the same single WITHDRAWN value. Reusing it for a maker-checker
   rejection is a direct continuation of that existing, deliberate
   design choice, not a stretch of it.
2. WITHDRAWN is already terminal (OFFER_TERMINAL_STATUSES) and already
   blocks every further mutation -- exactly the guarantee a rejected
   offer requires (non-issuable, non-hireable) -- with zero new guard
   code.
3. DECLINED was considered and rejected as a candidate: DECLINED
   carries a specific, different, already-established meaning --
   the CANDIDATE responded negatively to a SENT offer (set only by
   recordOfferResponse(), requires prior status SENT, sets declinedAt).
   Reusing DECLINED for an employer-side Tier 2 rejection that can occur
   before the offer is ever SENT would be actively misleading -- it
   would falsely imply a candidate was informed and responded. DECLINED
   is excluded from this design for this reason.
4. The TRUE cause (Tier 2 rejection specifically, as opposed to a
   voluntary withdrawal) is preserved with full fidelity in the
   correlated, immutable audit trail -- DECISION_CASE_REJECTED and
   APPROVAL_DECISION_REJECTED (Decision 23), correlated to the Offer via
   entityId/decisionCaseId -- exactly the existing M39 correlation-not-
   duplication pattern. Offer.status remains a coarse business-state
   field, as it already is today; the audit trail is where cause-level
   fidelity belongs.
```

**Precision note on "unmodified" in the table above:** every occurrence of
"unmodified"/"unchanged" in the transition table refers strictly to the
specific `Offer.status` write and its business-state semantics being
reused as-is — it does **not** mean the surrounding service method or its
live authorization boundary is unmodified. Implementation will still:

```text
- Modify submitOffer(): preserves the DRAFT -> PENDING_APPROVAL write
  itself, but implementation connects submission to DecisionCase/
  ApprovalRequest creation (Decision 10) and changes its live RBAC
  boundary (Decision 8/18)
- Modify sendOffer(): preserves the APPROVED -> SENT write itself, but
  implementation adds approval-request revalidation (Decision 11),
  removes System Administrator from its live RBAC boundary (Decision 9),
  and upgrades its audit write to logEventStrict() (Decision 23)
- Modify hire.service.ts: preserves its existing atomic business
  mutation and 8-precondition chain, but implementation adds approval
  revalidation and consumption (Decision 13), narrows its live RBAC
  boundary to HR Director only (Decision 9), and upgrades its audit
  writes to logEventStrict() (Decision 23)
```

No enum or migration change is authorized by this decision. Every
`Offer.status` transition above reuses an existing, already-implemented
write **as a data-layer operation** unmodified except for the trigger
source (an `ApprovalService` outcome, rather than a single caller) and
the two new conditional transitions (`DRAFT` on Needs Information,
`WITHDRAWN` on Rejection), neither of which requires new status values,
new terminal-status logic, or new editability logic — both fully reuse
logic `updateOffer()` and `withdrawOffer()` already enforce today. The
service methods that perform these writes are not wholly unmodified —
see the precision note above.

This mapping requires no new `OfferStatus` value and no Prisma migration.
Implementation may reconfirm exact file/line locations, but the required
behavior itself — every transition in the table above — is fully governed
by this decision and is not open for implementation-time redesign.

## Decision 16 — Elevated-Risk Fail-Closed Behavior

M40 must not create automatic or manual risk-detection functionality — M42
owns deterministic Policy Guard behavior. If an M40 `DecisionCase` already
contains any governed `DecisionCaseRiskTrigger` requiring Tier 3
oversight (created by some other, already-governed mechanism outside
M40's scope — M40 adds no new trigger-creation path):

```text
- Routine execution must fail closed at both the issuance boundary
  (Decision 11) and the hire-execution boundary (Decision 13)
- The offer must not be issued
- The hire must not execute
- M40 must return a deterministic elevated-review-unavailable outcome
  (audited via Decision 23's single new event type, RECRUITING_
  APPROVAL_EXECUTION_BLOCKED, with blockReason: ELEVATED_RISK_PENDING)
- The case must remain preserved, unmutated, for later governed handling
```

M40 does not activate the Independent Oversight Reviewer and does not
expose a dormant Compliance Officer approval path as though oversight
were operational — a fail-closed block, not a substitute approval, is the
only authorized response to a pending Tier 3 requirement.

## Decision 17 — Recruiting-Scoped API Design; Retirement of POST /offers/:id/approve

No generic route is authorized. `/decisions/:caseId`, `/approval-
requests/:id`, and `/decisions/:caseId/approval-requests/:requestId/
decisions` remain **unauthorized and out of scope** — such routes would
activate the M38 foundation across future domains beyond M40, contrary to
Decision 1 and `GD-M38-1` Decision 19's non-activation guarantee for every
other domain. The M40 HTTP surface is recruiting-scoped and must reject
any case whose `subjectType` is not `OFFER`.

**`POST /offers/:id/approve` is not repurposed for the new decision
route.** An endpoint literally named `/approve` becomes misleading the
moment it can also record `REJECTED` or `NEEDS_INFORMATION` — retaining
the name while changing its meaning would itself be a form of ambiguity
this decision must not introduce. **Final disposition: `POST
/offers/:id/approve` is retired and removed** as part of M40's
intentionally breaking contract with the pre-M40 single-actor approval
model, not left as a compatibility stub. A removed route returns NestJS's
ordinary 404 for an unmapped path — this achieves "never a functioning
bypass" with no additional code, no additional test surface, and no
additional maintenance burden versus authoring and maintaining a stub
controller method whose only job is to explain that the route is gone.

Minimum authorized surface, reconciling against existing controller
conventions (all under the existing `OfferController`/`HireController`
route namespaces; no new top-level route segment):

```text
POST /offers/:id/submit
  -- Final-offer submission (EXISTING route; role mapping changes per
     Decision 8; now additionally creates/retrieves the DecisionCase and
     submits the Tier 2 ApprovalRequest). Capability: offers:submit.

GET  /offers/approvals
  -- Pending-my-approval list: DecisionCases where the calling user is
     the preparer or qualifies for an outstanding requirement. NEW route.
     Capability: offers:approvals-read (Decision 18 -- NOT offers:read).

GET  /offers/:id/approval-case
  -- Recruiting approval-case detail: frozen evidence summary,
     requirement statuses, current ApprovalRequest status. NEW route.
     Capability: offers:approvals-read (Decision 18 -- NOT offers:read).

POST /offers/:offerId/approval-requirements/:requirementId/decision
  -- Records ONE Tier 2 decision (GRANTED/REJECTED/NEEDS_INFORMATION)
     from the calling user against the ONE named, open requirement they
     are attempting to satisfy. NEW route -- REPLACES
     POST /offers/:id/approve entirely (removed above). Capability:
     offers:approve (Decision 18 -- reused; see that decision for why
     its semantics still match). Never completes an offer's approval
     from a single call -- completion requires BOTH requirements to
     reach GRANTED, enforced server-side by ApprovalService exactly as
     Decision 10/15 describe.

POST /offers/:id/send
  -- Offer issuance (EXISTING route; role mapping changes per Decision
     9; precondition extended per Decision 11). Capability: offers:issue.

POST /applications/:id/hire
  -- Hire execution (EXISTING route; role mapping changes per Decision
     9; precondition chain extended per Decision 13). Capability:
     hire:authorize.
```

**Net route-count change: minus one, plus three** (`POST
/offers/:id/approve` removed; `GET /offers/approvals`, `GET
/offers/:id/approval-case`, and `POST /offers/:offerId/approval-
requirements/:requirementId/decision` added) — reflected as a net +2 in
Decision 29's projected endpoint count, not counted as three additions
against an unchanged baseline.

**`POST /offers/:offerId/approval-requirements/:requirementId/decision`
— exact contract:**

```text
Path parameters: offerId, requirementId (both server-verified below --
  neither is trusted as sufficient authorization on its own)
Request body (only these two fields; no client-supplied authority claim
  of any kind is accepted):
  decision: 'GRANTED' | 'REJECTED' | 'NEEDS_INFORMATION'
  reason: string (non-empty, matching ApprovalService's existing
    validation)
Actor identity: derived exclusively from the authenticated JWT
  (@CurrentUser(), the same pattern hire.controller.ts already uses --
  never from the request body)

Server-side verification, in order, before any decision is recorded:
  1. Tenant -- offer looked up by (id, tenantId) from the JWT only
     (SEC-003, unchanged discipline); absent/cross-tenant/soft-deleted
     -> 404 OFFER_NOT_FOUND
  2. Offer <-> DecisionCase relationship -- the DecisionCase is DERIVED
     from the offer (subjectType: OFFER, subjectId: offer.id,
     tenantId), never accepted as a client-supplied ID; no case found
     -> 409 NO_GOVERNED_CASE (the offer was never submitted through the
     governed flow)
  3. Active ApprovalRequest -- the CURRENT (latest-version, non-
     SUPERSEDED) request for that case is derived server-side; if its
     status is not PENDING -> 409 with ApprovalService's own
     INVALID_REQUEST_LIFECYCLE_STATE outcome, unmodified
  4. Requirement-belongs-to-request -- requirementId is verified to
     belong to THIS exact request (not a stale, superseded version's
     requirement) -> 404 REQUIREMENT_NOT_FOUND otherwise
  5. Requirement remains unanswered -- ApprovalService's own
     RequirementAlreadyDecidedViolation, unmodified
  6. Current actor qualification -- ApprovalService's own
     assertHumanActorQualifiesForCategory(), unmodified (confirms the
     actor is ACTIVE, in-tenant, and holds a role that
     authority-category-mapping.ts maps to the requirement's category)
  7. Actor permitted to fill that specific authority category -- same
     mechanism as (6); a Hiring Manager may only satisfy a
     DEPARTMENT_OR_HIRING_AUTHORITY requirement, never an HR_AUTHORITY
     requirement, and vice versa for HR Director
  8. Preparer-separation -- ApprovalService's existing check (currently
     implemented for Tier 1/Tier 3; Decision 28's validation gate
     requires confirming or extending this check to Tier 2 specifically
     before implementation is considered complete)
  9. Distinct-decider -- the existing
     idx_approval_decisions_request_decider database unique index,
     unmodified
  10. No elevated-risk execution bypass -- structurally guaranteed by
      ApprovalService's own fail-fast design: GRANTED only resolves the
      REQUEST to APPROVED once EVERY requirement on it -- including any
      Tier 3 INDEPENDENT_OVERSIGHT_REVIEWER requirement a pending risk
      trigger may have added (Decision 16) -- has a GRANTED decision;
      since M40 activates no Independent Oversight Reviewer profile, no
      live actor can ever grant a Tier 3 requirement, so a case carrying
      one can never reach APPROVED through this route at all. Decision
      16's issuance/hire-execution-time re-check remains as
      defense-in-depth for evidence that changes after this point, not
      as the sole safeguard.

Deterministic outcomes returned (mirroring ApprovalService's existing
  discriminated union): SUCCESS_PENDING (one of two requirements now
  granted; Offer.status unchanged, Decision 15), SUCCESS_REQUEST_APPROVED
  (Offer.status -> APPROVED, same transaction, Decision 22), SUCCESS_
  REQUEST_REJECTED (Offer.status -> WITHDRAWN, same transaction), SUCCESS_
  REQUEST_NEEDS_INFORMATION (Offer.status -> DRAFT, same transaction), and
  the existing REQUEST_NOT_FOUND / INVALID_REQUEST_LIFECYCLE_STATE /
  REQUIREMENT_NOT_FOUND / REQUIREMENT_ALREADY_DECIDED / ACTOR_* /
  PREPARER_SEPARATION_VIOLATION / TIER_INDEPENDENCE_VIOLATION /
  DUPLICATE_DECIDER_ON_REQUEST error outcomes, unmodified.
```

`GET /offers/approvals` must be registered before any
`GET /offers/:id`-shaped route in the controller's method-registration
order, following the exact static-route-before-`:id` ordering discipline
`GD-M39-1` already established and validated for this codebase — a
route-ordering defect here would let `/offers/approvals` be swallowed by
`/offers/:id`.

**No functioning bypass route is left.** `POST /offers/:id/approve` no
longer exists; its single-actor-completes-alone behavior is eliminated by
removal, not by behavior change to a route of the same name.

## Decision 18 — Capability Design

**No per-role approval capability is created.** `hire:approve-department`
and `hire:approve-hr` style capabilities remain explicitly rejected — the
`ApprovalRequirement`'s `AuthorityCategory`, not the capability name,
determines which slot a human may satisfy; `RolesGuard`/`@RequireRoles()`
gates coarse endpoint access exactly as it does today, and
`ApprovalService`'s own qualification check
(`assertHumanActorQualifiesForCategory`) determines fine-grained slot
eligibility, unchanged.

**Correction to the original draft:** the original draft proposed reusing
`offers:read` (current mapping: System Administrator, HR Director,
Recruiter, Compliance Officer) to gate the two new read routes. This is
now rejected — `offers:read`'s existing mapping includes both System
Administrator and Compliance Officer, and reusing it would let both gain
routine recruiting-approval-case visibility (frozen evidence, requirement
decision status) merely through their existing role, directly
contradicting Decision 9 and Decision 24's explicit visibility
constraints. Reusing an action capability for an unrelated, more
sensitive read endpoint merely to avoid a catalog addition is rejected in
favor of correct semantic authorization, per this decision's own
governing instruction. **One new, narrowly scoped read capability is
authorized: `offers:approvals-read`** — following the live
`resource:action` convention exactly as `offers:record-response` already
demonstrates a hyphenated multi-word action is permitted.

Every proposed M40 endpoint, reconciled against the live M36 catalog:

| Route | Purpose | Effective `@RequireRoles()` | `@RequireCapability()` | Current mapping | Proposed post-M40 mapping | Mapping changes | Capability accurately describes route |
|---|---|---|---|---|---|---|---|
| `POST /offers/:id/submit` | Final-offer submission; creates/retrieves DecisionCase, submits Tier 2 ApprovalRequest | Recruiter, Hiring Manager, HR Director | `offers:submit` | SA, HR Director, Recruiter | Recruiter, Hiring Manager, HR Director | Yes (SA removed, Hiring Manager added) | Yes — "who may submit a final offer for approval" is unchanged in meaning, only the qualifying role set changes |

## Decision 20 — Decision-Case Uniqueness, Idempotency, and Concurrency

The existing M38 entities and idempotency design are reused as-is; no new
table, column, or migration is authorized by this decision.

**Idempotency strategy:** the `DecisionCase.idempotencyKey` must be
**server-derived and deterministic** — never an arbitrary client-provided
key — computed from the governed offer's stable identity (e.g., a fixed
function of `tenantId` and `offer.id`, evaluated identically on every
submission attempt for that offer). Combined with the existing
`idx_decision_cases_tenant_idempotency` unique index
(`(tenant_id, idempotency_key)`), this guarantees **exactly one active
final-offer authorization case per governed offer** at the database layer,
with no new constraint required.

The following duplicate/substitution scenarios are already prevented by
existing, unmodified M38/hire/offer mechanisms — no additive constraint or
schema change is required for any of them:

```text
- Concurrent duplicate cases for the same offer: the server-derived
  idempotency key + existing unique index (above)
- Concurrent duplicate pending requests: idx_approval_requests_tenant_
  case_pending (existing, unmodified)
- Multiple decisions by the same user in one request:
  idx_approval_decisions_request_decider (existing, unmodified)
- Execution of a superseded request: Decision 11/13's re-check that the
  current ApprovalRequest.status === 'APPROVED' (not merely "latest
  version") at issuance/hire-execution time
- Cross-tenant subject substitution: assertGovernedSubjectExists()'s
  existing tenant-scoped lookup (unmodified)
- Linking approval from one offer to another application: Decision 13's
  requirement that the hire endpoint DERIVE the DecisionCase from the
  application's own linked ACCEPTED offer -- never accept a client-
  supplied decisionCaseId
- Repeated issuance: sendOffer()'s existing OFFER_NOT_APPROVED
  precondition (status must be APPROVED; once SENT, re-send is rejected)
- Repeated hiring: hire.service.ts's existing APPLICATION_ALREADY_HIRED
  idempotency guard (Precondition 2), which is also the mechanism that
  prevents re-consuming an already-consumed authorization (Decision 13)
```

**If a future implementation pass discovers the live M38 constraints
cannot, in fact, prevent duplicate offer cases under real concurrency**
(e.g., a race between the server-derived-idempotency-key check and the
unique-index write), the smallest additive fix is a database-layer
`P2002` fallback identical to the pattern `ApprovalService.
submitApprovalRequest()` already uses for its own pending-request race —
no generic execution framework or new entity is authorized as a
workaround.

## Decision 21 — No Execution Scheduler

No scheduled hire- or offer-execution reconciliation worker is authorized.
If offer issuance or hire execution fails, the relevant deterministic
transaction (Decision 22) must roll back completely; the approved
authorization remains available if still valid (i.e., still `APPROVED`
and not superseded); an authorized human may retry the explicit action;
every retry must revalidate the approval and current business state from
scratch (Decisions 11 and 13's preconditions apply identically on retry);
and duplicate execution remains blocked through the existing transactional
status and uniqueness checks (Decision 20). This is not autonomous
execution — no `ActionExecution`, `VerificationResult`, or other generic
execution entity is authorized in M40.

## Decision 22 — Transaction Boundaries

Three separate atomic transaction boundaries are authorized:

```text
Transaction 1 -- Decision recording + conditional Offer transition
  Extends ApprovalService.recordApprovalDecision()'s existing
  transaction (or wraps it, if recordApprovalDecision() is given an
  optional external `tx` parameter -- an additive, non-breaking
  signature change) to also perform, in the SAME transaction as the
  triggering ApprovalDecision write, a CONDITIONAL Offer.status
  transition keyed to ApprovalService's own outcome (Decision 15):
    - SUCCESS_PENDING (one requirement granted, one still open) -> no
      Offer.status write of any kind; Offer remains PENDING_APPROVAL
    - SUCCESS_REQUEST_APPROVED -> Offer.status -> APPROVED
    - SUCCESS_REQUEST_REJECTED -> Offer.status -> WITHDRAWN
    - SUCCESS_REQUEST_NEEDS_INFORMATION -> Offer.status -> DRAFT
  Every branch is the SAME single transaction as the decision write --
  none is a separate follow-up transaction.

Transaction 2 -- Explicit offer issuance
  sendOffer()'s existing transaction, extended to revalidate the
  ApprovalRequest's APPROVED-and-not-superseded status before
  transitioning Offer.status APPROVED -> SENT (Decision 11).

Transaction 3 -- Explicit hire execution
  hire.service.ts's existing atomic 4-write $transaction, extended with
  Decision 13's additional preconditions, but otherwise UNCHANGED --
  employee creation, application transition to HIRED, vacancy transition
  to FILLED, competing-application disposition, and related position-
  assignment behavior are all preserved exactly as GD-M19-1 Decisions
  5-9 already require. The current precondition chain is not weakened.
```

Each transaction must: revalidate tenant and current state; use strict
audit writing (`logEventStrict()`, Decision 23); roll back completely if
its strict audit write fails; reject stale or superseded authorization;
remain idempotent; and prevent partial business-state changes. No
transaction boundary spans more than one of the three groups above — an
approval decision never directly triggers issuance or hire execution as
part of the same transaction as the decision itself, satisfying Decision
6's approval/execution-separation requirement.

## Decision 23 — M39 Strict-Audit Integration and Metadata Rules

Existing M38 approval and decision-case audit events are reused for the
entire routine lifecycle — **an inventory of the existing 128-value
catalog was performed before any new value was considered, resolving any
apparent tension between "no new event types" and "M40 adds new event
values" by inventorying first and adding only where no existing event
accurately represents the governed action:**

```text
Already sufficient, reused unmodified, no new value needed:
  DECISION_CASE_CREATED, DECISION_CASE_EVIDENCE_ATTACHED,
  APPROVAL_REQUEST_SUBMITTED, APPROVAL_REQUEST_SUPERSEDED,
  APPROVAL_DECISION_GRANTED, APPROVAL_DECISION_REJECTED,
  APPROVAL_DECISION_NEEDS_INFORMATION, DECISION_CASE_NEEDS_INFORMATION,
  DECISION_CASE_RESUBMITTED, DECISION_CASE_APPROVED,
  DECISION_CASE_REJECTED -- the full M38 DecisionCase/Approval lifecycle
  already fires the correct event at each transition described in
  Decisions 10 and 15; the Offer-side status fact (e.g., "reverted to
  DRAFT," "moved to WITHDRAWN") is correlated to its DecisionCase-level
  cause via entityId/decisionCaseId, following the established M39
  correlation-not-duplication pattern, rather than by a second,
  denormalized Offer-side event.
  RECRUITING_OFFER_APPROVED, RECRUITING_OFFER_SENT,
  RECRUITING_OFFER_WITHDRAWN, RECRUITING_CANDIDATE_HIRED,
  WORKFORCE_EMPLOYEE_CREATED_FROM_HIRE, WORKFORCE_VACANCY_FILLED_
  FROM_HIRE, WORKFORCE_EMPLOYEE_POSITION_ASSIGNED_FROM_HIRE -- reused
  unmodified for their existing business-state meanings, each UPGRADED
  from best-effort logEvent() to logEventStrict() inside the relevant
  Decision 22 transaction, because each becomes a governed human
  mutation in the M37/M38/M39 sense for the first time under M40.

Genuinely new, confirmed still necessary after this inventory, because no
existing event represents an execution-TIME authorization-validity block
(as opposed to a lifecycle-decision event):
  RECRUITING_APPROVAL_EXECUTION_BLOCKED -- fired ONLY when a Decision 11
  issuance attempt or a Decision 13 hire-execution attempt is
  deterministically rejected by a precondition check BEFORE any mutating
  transaction is opened, because the approval authorization is invalid,
  stale, superseded, already consumed, or blocked by an unresolved
  elevated-risk trigger (Decision 16). Carries a closed-enum metadata
  field, blockReason, limited to ELEVATED_RISK_PENDING,
  STALE_AUTHORIZATION, ALREADY_CONSUMED, and SUPERSEDED. No PII, no
  compensation, no raw request payload, no raw error text.
```

**Blocked attempt vs. failed execution — an explicit distinction:** a
"blocked" outcome (`RECRUITING_APPROVAL_EXECUTION_BLOCKED`) means a
precondition check refused the action deterministically and no mutating
transaction was ever opened — nothing was attempted, so there is nothing
to roll back and no ambiguity about state. A "failed execution" (e.g., a
database error mid-transaction) is a different, pre-existing case already
handled by each transaction's own rollback and `INTERNAL_ERROR`-style
outcome (Decision 22) — it is never represented by this event, and this
event's own wording and metadata must never imply that a mutation was
attempted or partially applied. Readers of this event must be able to
conclude, from the event type alone, that the underlying `Offer`/
`Application`/`Employee` state is unchanged.

**Strict vs. operational classification, and why:** this event is emitted
via best-effort `logEvent()` (or the narrow, non-recursive
`logOperationalEvent()` path, at implementation's discretion between the
two, provided the non-recursion rule is preserved), **never**
`logEventStrict()`. Reasoning: `logEventStrict()` is reserved for writes
inside a transaction that itself mutates governed state (Decision 22) —
if that audit write fails, the whole transaction rolls back, because a
governed mutation must never occur without its audit record. A blocked
attempt, by definition, opens no such transaction — there is no mutation
whose atomicity the audit write must protect. Treating this event as
strict would incorrectly imply it participates in state-changing
atomicity it has no role in.

Exactly **one** new `AuditEventType` value is authorized: **
`RECRUITING_APPROVAL_EXECUTION_BLOCKED`**, projecting the confirmed
128-value M39 baseline to **129** — see Decision 29 for the full,
independently reproducible arithmetic. This is a final, governed count,
not an open question.

Every mutation this decision authorizes inside a Decision 22 transaction
must use `logEventStrict()` inside that same transaction — this applies
to `RECRUITING_OFFER_APPROVED`, `RECRUITING_OFFER_SENT`, `RECRUITING_
OFFER_WITHDRAWN`, `RECRUITING_CANDIDATE_HIRED`, `WORKFORCE_EMPLOYEE_
CREATED_FROM_HIRE`, `WORKFORCE_VACANCY_FILLED_FROM_HIRE`, `WORKFORCE_
EMPLOYEE_POSITION_ASSIGNED_FROM_HIRE`, and every M38 `DECISION_CASE_*`/
`APPROVAL_*` event this decision reuses. `RECRUITING_APPROVAL_EXECUTION_
BLOCKED` is the one explicit, reasoned exception, per the classification
above. Correlation is achieved via the existing `entityType`/`entityId`
fields plus tenant-scoped relational traversal through `ApprovalRequest.
decisionCaseId` — the exact mechanism `GD-M39-1` already established; no
new denormalized correlation column is authorized. Approval-request
correlation, approval-decision correlation, offer correlation,
application correlation, and candidate/vacancy correlation are all
satisfied through this existing mechanism without any PII duplication.

**The M39 response allowlist (`audit-response-allowlist.ts`) must be
updated narrowly and fail closed** to add exactly one new per-event-type
entry for `RECRUITING_APPROVAL_EXECUTION_BLOCKED`, exposing only
`blockReason` from its metadata — every other key remains excluded by
default, per the allowlist's existing fail-closed design. **Never expose
compensation, candidate PII, separation information, raw request bodies,
or internal errors through audit metadata**, for this or any existing
event type this decision touches.
