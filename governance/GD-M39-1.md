# Background

## Why This Decision Exists

`GD-M35-1` Decision 9 identified that `AuditService.logEvent()` is
write-only, silently swallows its own failures, and has no read endpoint
anywhere in the repository — insufficient to support a profile whose
defining purpose is reviewing what happened, and insufficient to satisfy
the audit trail a privilege-granting mechanism like elevation requires
before production activation. `GD-M37-1` and `GD-M38-1` each built real,
dormant, CI-confirmed foundations (elevation sessions; decision cases and
tiered approval) while explicitly declining to claim any part of M39 was
thereby satisfied. M39 is that step: the first milestone in this roadmap
authorized to add a real, if narrowly scoped, HTTP read surface and exactly
two governed mutation actions, closing the audit-read/recovery/integrity
gap `GD-M35-1` identified without activating anything M39 does not itself
own.

## What the Readiness Assessments and Project-Owner Review Confirmed

Three rounds of direct, repeated re-inspection of the running codebase
established the following facts, which this decision treats as
authoritative (full citations in References above):

- 122 `AuditEventType` values exist today; 91 real, executable audit-write
  call sites exist (71 `logEvent()`, 20 `logEventStrict()`) across 19
  production files; zero audit-read endpoint, zero audit viewer, zero
  audit-related capability, and zero scheduler/queue/worker/outbox
  infrastructure exists anywhere in this repository.
- Exactly one PostgreSQL role is used for the application runtime, schema
  migrations, and table ownership simultaneously — meaning a simple
  privilege `REVOKE` against that role is not a durable protection (the
  owning role can always `GRANT` the privilege back to itself), and a
  database trigger, not a grant revocation, is the truthful minimum
  append-only control available without introducing new deployment
  infrastructure.
- The `updatedFields`/`fieldsChanged` metadata pattern used across seven
  production services is a real, named, field-names-only PII-safety
  convention ("the EMP-401 pattern"), confirmed by direct source trace,
  not assumed; exactly one metadata value across all 91 call sites —
  `separationReason` on `WORKFORCE_EMPLOYEE_SEPARATED` — is genuinely
  free-form and must never be exposed by any M39 read surface, under any
  role.
- The governed M36 authorization baseline (62 capabilities, 175
  role-permission pairs, 73 protected endpoint methods, 127 role subsets,
  9,271 parity comparisons, 7 canonical role-set combinations) is
  confirmed live and unchanged; a separate, pre-existing, M39-unrelated
  documentation imprecision was found and corrected during this review —
  the "70 executable `@RequireRoles()` occurrences" figure is confirmed
  correct once the 7 explanatory-comment lines among the 77 raw textual
  matches are properly excluded; this is recorded as a documentation
  clarification, not a repository defect.
- `apps/web`'s `admin` route segment has no shared authorization layout —
  each page enforces its own role check — so a new audit viewer belongs at
  a neutral route outside `/admin` rather than inside it, to avoid any
  accidental association with the System-Administrator/HR-Director-
  oriented `admin` index.
- `directives/07_compliance_rules.md` already establishes a binding
  seven-year minimum compliance-record retention floor, resolving what
  would otherwise be an open retention-duration question without
  inventing a new figure for this decision.

## Decision 5 — Audit Occurrence Time Versus Recording Time

`AuditEvent` gains two distinct, non-conflatable timestamps:

```text
occurredAt  — when the underlying audited business event or read
              actually happened. Generated, together with the eventual
              row's id, BEFORE the first write attempt — at the call
              site inside logEvent()/logEventStrict()/
              logOperationalEvent() themselves, so no change to any of
              the 91 existing call sites' arguments is required.
createdAt   — when the row became durable in audit.audit_events. On a
              first-attempt success these are effectively simultaneous;
              on a recovered write, createdAt reflects the true later
              insertion time while occurredAt and id are carried over
              unchanged from the original attempt (Decision 11).
```

Binding requirements: `AuditWriteFailure` stores both `eventId` and
`occurredAt`, populated once at first failure and reused verbatim on every
retry — the eventual `AuditEvent.id` **is** that same `eventId`. The
viewer displays `occurredAt` as the primary, headline time and surfaces a
visible "recorded late" indicator whenever `createdAt` materially differs
from `occurredAt` (Decision 20). Cursor pagination uses **`(createdAt,
id)`** — insertion order, not event-occurrence order, is what must be
monotonically stable for a live-writing, append-only table's cursor.
Date-range filtering uses **`occurredAt`**. Every pre-M39 row is
deterministically backfilled with `occurredAt = createdAt` (Decision 23)
— never fabricated to any other value.

## Decision 6 — Fixed Retention Enforcement

Per final project-owner decision: M39 enforces a **fixed, non-configurable
seven-year minimum** retention floor, sourced from the existing binding
directive `directives/07_compliance_rules.md:411-419` ("Compliance
records retained: 7 Years Minimum"), not invented for this decision.

```text
retentionUntil = occurredAt + INTERVAL '7 years' — always derived by a
  database trigger, never accepted from any HTTP DTO, service input, or
  other caller-supplied value, and never merely filled when absent — the
  trigger unconditionally overwrites whatever value (if any) was
  supplied.
Records remain in place. No deletion. No archive movement. No purge
  endpoint or worker of any kind exists in M39.
No tenant-configurable shortening of the seven-year floor — none exists,
  and no mechanism to request one is built.
No RetentionPolicy table — the policy is fixed and requires no per-
  tenant or per-record configurable state to represent; retentionUntil
  is fully computed per-row from occurredAt.
Legal hold is explicitly deferred — M39 already blocks all update/delete
  unconditionally (Decision 7), so nothing further is needed yet; the
  schema/design must not, and does not, preclude adding a legalHold
  column later.
Future archival or deletion of any audit record requires its own,
  separate governance decision — this decision authorizes none.
```

Migration sequencing, binding and exact:

```text
1. Add occurredAt and retentionUntil as nullable columns.
2. Backfill existing rows: occurredAt = createdAt; retentionUntil =
   occurredAt + INTERVAL '7 years'.
3. Verify zero rows remain with either field null.
4. Set both fields NOT NULL.
5. Install the insert trigger (Decision 6's derivation rule) only after
   step 4 succeeds — never before every existing row already satisfies
   the invariant the trigger will enforce going forward.
```

## Decision 7 — Bounded Append-Only Protection

A database trigger, not a privilege revocation, is the authorized M39
control:

```text
CREATE FUNCTION audit.prevent_audit_mutation() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'audit.audit_events rows are append-only and immutable';
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER audit_events_prevent_mutation
  BEFORE UPDATE OR DELETE ON audit.audit_events
  FOR EACH ROW EXECUTE FUNCTION audit.prevent_audit_mutation();
```

This is the truthful minimum control available without new deployment
infrastructure, because — confirmed directly from `.env`,
`docker-compose.yml`, `Dockerfile`, and CI configuration — exactly one
PostgreSQL role (`govplatform`) serves as application runtime role,
migration role, and table owner simultaneously; a `REVOKE UPDATE, DELETE`
against that same role is not durable, since the owning role can always
`GRANT` the privilege back to itself. **This decision states explicitly,
and no future document may soften:**

```text
The trigger provides bounded protection against ordinary application
  behavior and accidental code paths — confirmed sufficient, since every
  one of the 91 real call sites only ever calls .create(), never
  .update() or .delete(), on auditEvent.
The trigger does NOT protect against the database owner, a Postgres
  superuser, or anyone able to directly disable or drop the trigger.
This is bounded tamper evidence. It is NOT absolute immutability, and no
  future document may describe it as such.
```

**Database-role separation between the application runtime and migration
credential is explicitly excluded from M39's scope.** It is recorded here
only as a **named future security-hardening recommendation**, requiring
its own, separately authorized infrastructure decision (touching
`apps/api/Dockerfile`, `infrastructure/docker/docker-compose.yml`, and
`.github/workflows/ci.yml`) before any such change may be made. No
Docker, Compose, or CI-credential file is in scope for M39.

## Decision 8 — Deterministic Per-Tenant Hash Chaining

A fully specified, versioned, deterministic SHA-256 hash-chain design
providing **tamper evidence, never tamper-proofing**:

```text
Algorithm: SHA-256, via Node's built-in crypto module (zero new
  dependency), lowercase hex output, 64 characters.
Canonical representation: a fixed-position JSON array (never delimiter-
  concatenated strings), UTF-8 encoded before hashing.
Fixed field order (14 elements): hashVersion, tenantId, sequenceNo (as
  its exact decimal string — BigInt is never passed to JSON.stringify
  directly, and never coerced to a lossy JS number), eventId, userId,
  action, entityType, entityId, result, canonicalMetadata, occurredAt,
  createdAt, retentionUntil, previousHash.
Null representation: any null element is emitted as JSON null at its
  fixed array position — the array never shrinks; position, not
  presence, carries meaning.
Canonical metadata: object keys recursively sorted (ascending UTF-16
  code-unit order) at every nesting depth before serialization; array
  element order is preserved exactly as-is, never sorted (arrays are
  data, never a canonicalization target); an object property whose value
  is undefined is omitted (native JSON.stringify behavior); an explicit
  null is preserved.
Timestamps: occurredAt, createdAt, retentionUntil each as their exact
  ISO-8601 UTC string (millisecond precision, Z suffix).
hashVersion: the array's first element, so a future canonicalization
  change can never collide with a differently-versioned row's hash;
  verification dispatches per-row via a version-keyed canonicalizer map,
  never a single assumed-current rule.
```

Sequencing and concurrency:

```text
AuditChainState(tenantId PK, lastSequence, lastHash, ...) — one row per
  tenant.
Race-safe first-write initialization: INSERT ... ON CONFLICT (tenant_id)
  DO NOTHING, followed by SELECT last_sequence, last_hash FROM
  audit.audit_chain_state WHERE tenant_id = :t FOR UPDATE, inside the
  same transaction as the eventual AuditEvent insert. Whichever
  concurrent first-writer's INSERT "wins" is irrelevant; every writer
  proceeds to the row-locking SELECT, which correctly serializes.
Genesis: the first chained row for a tenant has previousHash = NULL and
  sequenceNo = 1 — never a hash of a fixed genesis string.
Legacy pre-chain rows: sequenceNo/recordHash/previousHash/hashVersion
  all remain NULL for every row written before M39's chain activation —
  never fabricated, never treated as a break by verification.
```

Verification (`verifyTenantChain()`) must detect, beyond simple
recompute-and-compare: **missing sequence numbers / gaps** (non-
contiguous `sequenceNo` after ordering a tenant's chained rows),
**duplicate sequence numbers** (independent re-scan, defense-in-depth
beyond the unique constraint), **incorrect genesis placement** (not
exactly one `previousHash IS NULL AND sequenceNo = 1` row per tenant among
chained rows), and **final-row-versus-chain-state mismatch** (the last
walked row's `(sequenceNo, recordHash)` must equal
`AuditChainState.lastSequence/lastHash` for that tenant). **Verification
never repairs, rehashes, or rewrites any row it inspects** — a detected
break is reported, never silently corrected.

## Decision 9 — Additive Data Model

Three new tables, additive within the existing `audit` Postgres schema
(no new schema is created):

```text
AuditWriteFailure — one row per originally-failed logEvent() attempt:
  id (= the eventual AuditEvent.id, client-generated at first failure),
  tenantId, userId, action, entityType?, entityId?, result, metadata?,
  occurredAt, failureReason (sanitized, fixed vocabulary — never a raw
  DB driver error), status (AuditWriteFailureStatus), attemptCount,
  nextAttemptAt, claimedAt?, claimedBy?, attemptedAt, createdAt,
  updatedAt.

AuditWriteFailureAttempt — one row per automatic recovery attempt
  against a AuditWriteFailure row: id, tenantId, auditWriteFailureId (FK),
  attemptNumber, claimedBy, startedAt, completedAt?, failureCategory?
  (sanitized, fixed vocabulary), status (AuditWriteFailureAttemptStatus).
  Terminal rows (SUCCEEDED/FAILED) are immutable; no row is ever deleted.

AuditChainState — one row per tenant: tenantId (PK), lastSequence,
  lastHash?, nextVerificationAt, verificationClaimedAt?, lastVerifiedAt?,
  lastVerificationResult? (AuditChainVerificationResult, nullable before
  the first verification ever runs), updatedAt.
```

Three governed enums (never free-form strings, following the M37/M38
precedent of native Postgres enums for every lifecycle-shaped field):

```text
AuditWriteFailureStatus:          PENDING, IN_PROGRESS, RETRIED, ABANDONED
AuditWriteFailureAttemptStatus:   IN_PROGRESS, SUCCEEDED, FAILED
AuditChainVerificationResult:     OK, BROKEN
```

Six new, additive `AuditEvent` fields: `occurredAt`, `retentionUntil`
(Decisions 5-6), `sequenceNo`, `recordHash`, `previousHash`, `hashVersion`
(Decision 8). No existing `AuditEvent` field is altered, renamed, or
removed. **No `AuditEvent.decisionCaseId` column is authorized** (Decision
19). **No `RetentionPolicy` table is authorized** (Decision 6). **No
`AuditWriteFailureAttempt`-duplicating history table is authorized beyond
the one specified above.**

Tenant boundaries: every new table carries a bare-scalar `tenantId`
column, enforced at the service layer exactly as every existing table in
this codebase is (no cross-tenant read or write path is authorized for
any of the three). Immutability: `AuditEvent` rows are protected by
Decision 7's trigger; `AuditWriteFailureAttempt` terminal rows are
immutable by service-layer convention (no update path is authorized past
`SUCCEEDED`/`FAILED`); `AuditWriteFailure` and `AuditChainState` remain
ordinary mutable operational tables by design (their whole purpose is to
track in-flight and evolving state) and are explicitly outside Decision
7's append-only trigger.

## Decision 11 — Failed-Write Recovery: A Bounded, Not Absolute, Guarantee

`logEvent()`'s existing non-throwing caller contract is preserved exactly
— none of its 71 existing call sites, or any future one added by other
milestones, requires any change.

```text
Strict M37/M38 lifecycle writes (and the two new M39 human mutations,
  Decision 14) remain transactionally fail-closed exactly as today —
  unaffected by anything in this decision.
A recoverable logEvent() failure is durably journaled into
  AuditWriteFailure (Decision 9), preserving its original eventId and
  occurredAt (Decision 5).
Retry is automatic (Decision 13), idempotent (the pre-generated eventId
  is inserted via ON CONFLICT DO NOTHING, so a row can never be durably
  written twice), and database-coordinated across multiple application
  instances.
Terminal failures (ABANDONED, past a configurable maximum attempt count)
  are operator-visible via the recovery-status endpoint (Decision 16)
  and the coarse public health aggregate (Decision 21).
```

**Explicit, binding limitation — no future document may narrow or hide
this:** a **total PostgreSQL outage** occurring after the triggering
business operation has already committed can leave only a structured
application log entry. **This repository does not guarantee that log is
durable or queryable** — no log-aggregation or log-shipping system is
verified to exist, and none is assumed by this decision. **M39 cannot
durably recover that final failure window.** Closing it would require
either transactionally converting every `logEvent()` caller to
`logEventStrict()`'s same-transaction pattern (a large, cross-cutting
change to all 16 business services, disproportionate to M39's scope), or
an independent, externally-hosted durable sink outside Postgres's own
failure domain (genuinely new infrastructure, not authorized here). **This
decision does not claim complete or lossless audit-write recovery.** This
bounded guarantee is judged, and recorded here as, sufficient to satisfy
`GD-M35-1` Decision 9's "observability and recovery for failed audit
writes" wording — no other subsystem in this platform has a stronger
guarantee against total infrastructure failure either, and audit is not
held to a stricter standard than the rest of the platform.

## Decision 12 — Recovery-Attempt History

Every automatic retry creates a durable, immutable `AuditWriteFailureAttempt`
row (Decision 9):

```text
The claim transaction increments AuditWriteFailure.attemptCount and
  creates the new IN_PROGRESS attempt row atomically, together.
A successful replay transitions that same attempt row to SUCCEEDED and
  the parent AuditWriteFailure to RETRIED.
A failed replay transitions the attempt row to FAILED and the parent
  back to PENDING (rescheduled) or to ABANDONED past the maximum attempt
  count.
Terminal attempt rows (SUCCEEDED/FAILED) are immutable. No attempt row
  is ever deleted. Raw database driver errors are never stored anywhere
  — only a sanitized failureCategory from a fixed, governed vocabulary.
A crashed worker's stale IN_PROGRESS attempt is never silently left
  appearing active: claim-expiry logic closes it as FAILED with a
  sanitized category (e.g. WORKER_TIMEOUT) and a completion timestamp,
  preserving it as historical evidence, then creates the next-numbered
  attempt — the stranded row is never deleted or overwritten.
Requeue (Decision 14/16) never resets attemptCount and never alters any
  prior attempt row — the complete history survives every requeue.
```

No separate history-duplicating mechanism is authorized — the append-only
`AuditWriteFailureAttempt` trail, together with the governed
`AUDIT_WRITE_RECOVERY_*` audit events (Decision 22) `logOperationalEvent()`
writes after each terminal transition, is the complete and sufficient
attempt-history design.

## Decision 13 — Automatic Workers

`@nestjs/schedule` is authorized as **one new dependency** — an official
NestJS package requiring no external process, no new infrastructure
dependency (no Redis, no separate deployment topology), only an in-process
recurring timer. **This is an explicit, documented deployment-behavior
change: every running API instance will execute recurring background work
in addition to serving HTTP requests.** Scheduler execution must be
disabled or safely controlled during automated test runs (e.g., not
registered under a test `NODE_ENV`), to avoid interfering with existing
test-suite process lifecycle.

**Recovery worker:**

```text
Automatically invoked on a configurable interval and batch size.
Database-coordinated row claiming via SELECT ... FOR UPDATE SKIP LOCKED
  (or the exact Postgres equivalent) — safe across any number of running
  instances without any advisory-lock mutex.
Claim expiration for stuck IN_PROGRESS claims (Decision 12).
Exponential backoff, a configurable maximum attempt count.
Idempotent replay (Decision 11) — no duplicate original audit event is
  ever produced.
Crash/restart recovery is automatic and requires no special-case code —
  state lives entirely in Postgres.
```

**Chain-verification worker:**

```text
Automatically invoked, tenant-batched, using the identical
  claiming pattern against AuditChainState.nextVerificationAt.
Multi-instance-safe by the same FOR UPDATE SKIP LOCKED mechanism.
An hourly default interval, governed and configurable.
Persistent last-verification state and persistent BROKEN state on
  AuditChainState (Decision 9) — never auto-cleared once broken.
No automatic repair of any kind (Decision 8).
A manual, System-Administrator-only, tenant-scoped out-of-cycle
  verification request is authorized (Decision 16, endpoint 5) —
  it only advances nextVerificationAt; it never performs verification
  synchronously.
```

## Decision 14 — Strict Versus Operational Audit-Write Boundaries

One consistent rule, with no exception and no contradiction:

```text
logEventStrict() — extended, for the first time since GD-M37-1
  introduced it, beyond M37/M38's own lifecycle mutations to cover two
  new M39 human-initiated mutations:
    - Manual requeue: one transaction — verify the target row is
      ABANDONED and tenant-matched, flip AuditWriteFailure.status
      ABANDONED -> PENDING (history/attemptCount untouched), and write
      the AUDIT_WRITE_RECOVERY_REQUEUED event, all inside that same
      transaction. A failed audit write rolls back the entire
      transaction — the row remains ABANDONED.
    - Manual re-verification request: one transaction — resolve the
      caller's tenant from the authenticated JWT only, set
      AuditChainState.nextVerificationAt = now() for that tenant, and
      write the AUDIT_CHAIN_REVERIFICATION_REQUESTED event, inside that
      same transaction.
  It is no longer accurate to describe logEventStrict() as exclusive to
  M37/M38 — it is, and after M39 remains, the write path for every
  governed human-initiated mutation this platform defines.

logOperationalEvent() — a new, narrow, non-recursive path for worker-
  generated supplemental notifications ONLY: recovery succeeded,
  recovery abandoned, and chain-verification failed. Attempts exactly
  one write, participating fully in the hash chain. On its own failure,
  it NEVER creates a new AuditWriteFailure row (preventing recursive
  dead-lettering of dead-letter-adjacent events) — it only emits a
  structured application-log warning. It is invoked only AFTER the
  durable parent/attempt/chain state (Decisions 9, 12) is already
  committed in its own, separate transaction — its failure can never
  erase or roll back state that transaction already made durable.
```

No document produced under this decision may describe requeue as using
both write paths, or describe `logOperationalEvent()` as anything other
than a strictly supplemental, non-recursive notification mechanism.

## Decision 21 — Operational Visibility

The existing, confirmed-unauthenticated `GET /health` endpoint may expose
**only a coarse aggregate** (e.g. `auditIntegrity: 'ok' | 'degraded'`) —

### Binding Clarification — Decision 21 Health-Status Behavior

This decision's original text specified the response's *content*
restriction only, and was silent on whether a degraded aggregate should
also change `/health`'s own HTTP-facing status. That silence surfaced as a
genuine open question during implementation validation and was resolved by
the project owner at that time. This is recorded here as an approved
clarification of Decision 21, not a reopening or expansion of it:

```text
Audit-integrity degradation (a broken per-tenant hash chain, or an
  ABANDONED audit-write-recovery backlog) is explicitly NON-GATING for
  the application's /health HTTP status. A degraded auditIntegrity value
  is reported as data; it never causes /health to return a failing
  status, because no application restart can repair either condition —
  gating on it would risk orchestrator restart loops against a problem a
  restart cannot fix, which this platform's health-check contract does
  not exist to cause.
A broken chain or a recovery backlog MUST still surface the coarse
  auditIntegrity: "degraded" signal on /health — never silently absorbed
  into an "ok" report.
Operational alerting and the audit oversight interface (Decision 20,
  the recovery-status endpoint of Decision 16) — not application restart
  behavior — are the intended channels for carrying a degraded-integrity
  signal to an operator.
The response continues to expose only the coarse ok/degraded value —
  never tenant identifiers, record or failure IDs, event or failure
  counts, chain details, or raw errors — exactly as this Decision's
  original text already required.
```

Implemented as `AuditIntegrityHealthIndicator`, whose `isHealthy()` never
throws — it always reports `up` at the Terminus indicator level with the
coarse `auditIntegrity` value carried as data, so `HealthCheckService`'s
aggregate `/health` status is never flipped by this indicator alone. The
only condition that changes `/health`'s overall HTTP status remains
database unreachability, via the pre-existing `PrismaHealthIndicator`
(unmodified by M39).

## Decision 23 — Idempotency, Concurrency, and Migration Sequencing

```text

No destructive migration and no fabricated historical audit data is
  authorized anywhere in this decision.
```
