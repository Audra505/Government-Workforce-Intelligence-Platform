# Background

## Why This Decision Exists

`GD-M35-1` identified that a permanent, standing System Administrator
persona is a structural risk the target operating model intends to retire
in favor of temporary, audited, time-boxed elevation. Building that
mechanism requires a reusable data model and lifecycle service — the
"elevation/scoped-grant core" `GD-M36-1` Decision 19 already named as M37's
job. M37 is that step, scoped as narrowly and safely as verified repository
evidence allows, and explicitly forbidden from having any effect on a real
authorization decision until its own activation is separately governed and
until M39's audit prerequisite is operational.

## What the Readiness Assessment and Project-Owner Review Confirmed

Direct, repeated re-inspection of the running codebase (not reliance on
prior summaries) established the following facts, which this decision
treats as authoritative:

- No elevation-session implementation exists anywhere in the repository
  today (`grep -rli "elevation|scopedgrant|elevationsession"` across
  `apps/api/src` and `apps/api/prisma` returns nothing).
- `CapabilityGuard` remains registered only in `identity.module.ts`'s
  `providers`/`exports` arrays and is not attached to any `@UseGuards(...)`
  list, `APP_GUARD` provider, or bootstrap path anywhere.
- The live `permissions.catalog.ts` was re-counted at authorization time
  and confirmed to contain exactly **62** unique capability entries and
  exactly **175** total role-permission pairs across `CAPABILITY_ROLE_MAPPINGS`
  — matching `GD-M36-1`'s own confirmed figures exactly, with zero
  discrepancy.
- No MFA, TOTP, OTP, step-up, or reauthentication mechanism exists
  anywhere in `apps/api/prisma/schema.prisma` or `apps/api/src` (exhaustive
  grep, zero matches). `spec/07_security_architecture.md` itself contains
  no mention of step-up authentication — this is a `GD-M35-1`-introduced
  future requirement, not a currently specified or implemented capability.
- `AuditService.logEvent()` (`apps/api/src/audit/audit.service.ts:30-52`)
  is write-only, has no read method anywhere in the module, and swallows
  its own write failures via `try`/`catch` + `Logger.error`, deliberately
  never rethrowing (AUD-1300). No audit-read API, viewer, tamper detection,
  retention enforcement, or failed-write recovery exists.
- No scheduler, cron, or background-worker infrastructure exists anywhere
  in this codebase (confirmed independently by `GD-M34-1`'s own identical
  finding when it designed `WorkforceSignalSnapshot`'s write-on-query
  pattern for the same reason).
- No `User` hard-delete path was found in the inspected user-management
  application logic (`UsersService`, `UsersController`, and every
  `apps/api/src` call site referencing the `User` model). `UsersService`
  models account lifecycle exclusively through the `status` string column
  (`ACTIVE` ⇄ `SUSPENDED`, `ACTIVE`/`SUSPENDED` → `DEACTIVATED`,
  `DEACTIVATED` → `ACTIVE`); no `prisma.user.delete(...)` call exists
  anywhere in that application logic, and the schema's one existing FK to
  `User` (`UserRole.user`, `schema.prisma:395`) carries no
  `onDelete: Cascade` clause. A separate, unrelated dev-environment
  command (`npm run db:reset`, i.e. `prisma migrate reset --force`) does
  exist and performs a full destructive schema drop-and-reseed — this is
  an environment-reset tool, not an application-level per-user deletion
  path, and it would clear `ElevationSession` history exactly as it clears
  every other table, which is an accepted characteristic of a dev reset
  tool rather than a gap this decision's actor-reference design needs to
  solve. Within ordinary application operation, the platform deactivates
  users rather than deleting the actor references elevation history would
  rely on.

## Decision 4 — Internal-Service-Only Implementation Boundary

M37 builds an internal, dormant elevation-session foundation only.
**No HTTP controller, route, externally callable API, frontend interface,
or feature flag is authorized.** No new capability-management endpoint is
authorized. No M37 file may register, wire, or activate `CapabilityGuard`
on any controller, global guard provider, or application bootstrap path.
No M37 file may modify `RolesGuard`'s behavior or authority. No M37 file
may add a claim to `JwtPayload`/`RequestUser` or otherwise change JWT
issuance or contents. **No elevation record may influence a real
authorization decision during M37, under any condition.**

This is a deliberately narrower boundary than the readiness assessment's
own Section 10 recommendation (which left open the possibility of
dormant, capability-gated administrative endpoints) — that possibility is
explicitly withdrawn by this decision. M37 is internal-service-only, full
stop; any future endpoint surface is a decision for M38 or a later,
separately governed milestone to make.

## Decision 5 — Lifecycle States (Prisma Enums, Not Unrestricted Strings)

Elevation-session lifecycle state and per-capability-item decision state
are each represented by a governed Prisma enum, not a free-form status
string (a deliberate departure from the `Offer`/`Application` precedent's
`VarChar` status columns, justified because elevation-session states are
a small, closed, security-relevant set where the added compile-time and
database-level protection against an invalid or misspelled state value is
worth the reduced flexibility that VarChar status columns elsewhere in
this schema trade for).

**Session-level lifecycle enum** (name to be finalized at implementation
time, e.g. `ElevationSessionStatus`):

```text
REQUESTED           — initial state; every requested capability item is
                        attached (as PENDING) at creation; the session
                        remains REQUESTED until every attached item has
                        been decided (no item may remain PENDING once the
                        session leaves this state — see Decision 8)
APPROVED            — every requested capability item has been decided,
                        and at least one item is GRANTED
DENIED               — terminal; every requested capability item has been
                         decided, and none is GRANTED (i.e. every item is
                         individually DENIED)
CANCELLED            — terminal; requester withdraws before any capability
                         item has been decided (see Decision 12 for how
                         this differs from REVOKED)
ACTIVE               — lifecycle-active only; see Decision 20 for the
                         binding distinction between this state and any
                         real authorization effect
EXPIRED              — terminal; expiresAt has been reached
REVOKED              — terminal; explicit revocation actor and reason
                         recorded (see Decision 12 for who may revoke)
ACTIVATION_FAILED    — terminal; session failed to transition APPROVED → ACTIVE
                         (e.g. a concurrency conflict — see Decision 13)
```

**Per-capability-item decision enum** (e.g. `ElevationCapabilityDecision`):

```text
PENDING   — requested, not yet decided
GRANTED   — approved individually; contributes to the session's granted set
DENIED    — denied individually; excluded from the session's granted set
```

## Decision 6 — Lifecycle and Permitted Transitions

```text
REQUESTED  → APPROVED             (every attached capability item has been
                                     decided, AND at least one is GRANTED)
REQUESTED  → DENIED                (every attached capability item has been
                                      decided, AND none is GRANTED)
REQUESTED  → CANCELLED              (requester withdraws before any
                                       capability item has been decided —
                                       once even one item has been decided,
                                       the session must instead reach
                                       APPROVED or DENIED, never CANCELLED)

APPROVED   → ACTIVE                 (activation succeeds — see Decision 13)
APPROVED   → ACTIVATION_FAILED       (activation conflicts — see Decision 13)

ACTIVE     → EXPIRED                 (expiresAt reached; detected at
                                        evaluation time by whatever future
                                        consumer checks validity — see
                                        Decision 11 — never by a scheduler)
ACTIVE     → REVOKED                  (explicit actor action; revokedByUserId,
                                        revokedAt, revokedReason recorded)
```

All of `DENIED`, `CANCELLED`, `EXPIRED`, `REVOKED`, and `ACTIVATION_FAILED`
are **terminal and immutable** — no transition ever re-opens a terminal
record. Per Decision 12 (Revocation and Terminal-State Behavior), reaching
any terminal state requires a new `ElevationSession` request; there is no
"reactivate" or "re-request" transition on an existing terminal row.

No transition in this lifecycle causes any effect outside the
`ElevationSession`/`ElevationSessionCapability` rows themselves — see
Decision 17.

## Decision 7 — Tenant Isolation and Tenant-Only Scope (No Resource-Level Scoping)

Every `ElevationSession` row carries a mandatory `tenantId`, populated
exclusively from the acting user's JWT-derived tenant context — never from
a request body, query parameter, or path parameter, matching the SEC-003
discipline already enforced identically across every existing controller
and service in this codebase. All lookups, uniqueness constraints, and
idempotency keys (Decision 13) are scoped by `tenantId`. No cross-tenant
elevation session, grantee, requester, or approver reference is
permitted.

**M37 elevation sessions are tenant-scoped only.** No `scopeResourceId`,
department scope, candidate scope, employee scope, Decision Case scope, or
any other polymorphic resource reference is authorized in M37's data model
(Decision 8) — this is a deliberate departure from the readiness
assessment's own recommendation, which had proposed an optional
`scopeResourceId` for PII-capable capabilities. Because Decision 10's
allowlist excludes every PII-capable capability, no such narrowing field
is needed in M37 at all. Department, employee, candidate, resource, and
Decision Case scoping are explicitly deferred to M38 (Decision 22).

## Decision 8 — Normalized Data Model

**`ElevationSession`** — one row per elevation request/session.

| Field (conceptual) | Purpose |
|---|---|
| `id` | Primary key |
| `tenantId` | Mandatory tenant scope (Decision 7) |
| `requestedByUserId` | The human who submitted the request |
| `granteeUserId` | The human who would receive the elevation. **May equal `requestedByUserId`** — a person requesting elevation for themselves is the ordinary case — or may differ if the requester is submitting on another grantee's behalf (Decision 9) |
| `approvedByUserId` | Nullable until a decision is made; must differ from **both** `requestedByUserId` and `granteeUserId`, with no exception — Decision 9 |
| `revokedByUserId` | Nullable; set only on `REVOKED`. **Not required to be globally distinct from the other actor columns** — the grantee may revoke their own elevation (voluntary relinquishment), the original requester may revoke it, or a separately, independently authorized actor may revoke it. Decision 12 governs who is authorized to revoke |
| `status` | The session-level lifecycle enum (Decision 5) |
| `purpose` | Mandatory, non-empty justification text |
| `requestedAt` | Set at creation |
| `decidedAt` | Set on `APPROVED`/`DENIED` |
| `activatedAt` | Set on `ACTIVE` |
| `expiresAt` | Mandatory once `ACTIVE`; never indefinite (Decision 11) |
| `revokedAt` | Set on `REVOKED` |
| `revokedReason` | Set on `REVOKED` |
| `denialReason` | Set on `DENIED` |
| `stepUpAuthMethod` | Nullable; must remain null throughout M37 (Decision 16) |
| `stepUpVerifiedAt` | Nullable; must remain null throughout M37 (Decision 16) |
| `correlationId` | Nullable; reserved for a future audit/decision-case correlation link — not consumed by anything in M37 |
| `idempotencyKey` | Unique **within `tenantId`**, not globally (Decision 13) |
| `createdAt`/`updatedAt` | Standard timestamps |

**`ElevationSessionCapability`** — one row per requested capability item,
child of `ElevationSession`.

| Field (conceptual) | Purpose |
|---|---|
| `id` | Primary key |
| `elevationSessionId` | Foreign key to the parent `ElevationSession` |
| `permissionId` | **Foreign key to the existing `Permission` table** — capability identity is established by referential integrity to the live M36 catalog row, never by an uncontrolled string column |
| `decision` | The per-item decision enum (Decision 5); starts `PENDING` |

**Referential and uniqueness rules (binding):**

```text
Each requested capability item is created only once, at the moment the
  ElevationSession is submitted (status = REQUESTED) — every
  ElevationSessionCapability row for a session is created in that same
  request-time operation, each starting at decision = PENDING. No row is
  ever created afterward.

Each Permission may appear at most once per ElevationSession — a
  uniqueness constraint on (elevationSessionId, permissionId) prevents a
  duplicate capability-item row within the same session.

No ElevationSessionCapability row may be created after the session leaves
  REQUESTED, and no row's `decision` field may be created or exist as
  PENDING once the session leaves REQUESTED — every attached item must be
  individually decided (set to GRANTED or DENIED) while the session is
  still REQUESTED, and the session's own transition out of REQUESTED
  (Decision 6) is gated on that condition. The approval action may only
  update the `decision` field on EXISTING rows created at request time —
  it may never insert a new row, and may never substitute a different
  Permission for one that was not originally requested. This is the
  structural mechanism (not merely a service-layer check) that proves
  approved capabilities can never exceed those requested: the set of
  PermissionIds ever eligible for GRANTED is fixed at request time and is
  a fixed subset of the allowlist (Decision 10).

Once the session leaves REQUESTED, every ElevationSessionCapability row's
  `decision` field becomes immutable — no service method may change a
  GRANTED item to DENIED, a DENIED item to GRANTED, or otherwise revisit
  a capability-item decision after the session has moved to APPROVED or
  DENIED. This is the same terminal-immutability principle Decision 12
  applies to the session's own `status` field, applied at the child-row
  level.

The session's own "granted capability set" is always and only the
  distinct set of Permission rows referenced by its ElevationSessionCapability
  children whose decision = GRANTED. This is never stored as a separate,
  independently-writable field — it is always derived, and is therefore
  structurally a subset of the requested capability set (the full set of
  ElevationSessionCapability rows for that session) by construction, never
  merely by convention.

permissionId values are validated against the live M36 catalog, and
  further restricted to Decision 10's allowlist, at the time each
  ElevationSessionCapability row is created — never at read time, and
  never assumed valid by any downstream consumer.
```

This directly satisfies the binding requirement that capability storage
use referential integrity to `Permission` rather than an uncontrolled
`String[]` column, and that partial approval (retained by this decision,
per the explicit rules above) can never grant an unrequested capability.

## Decision 9 — Actor Roles: Who May Request, Be Granted, Approve, and Revoke

M37 distinguishes four actor roles on every `ElevationSession`, and binds
exactly which of them may or may not coincide:

```text
Requester (requestedByUserId) and Grantee (granteeUserId):
  MAY be the same person. Self-requested elevation — a person requesting
  temporary elevation for their own account — is the ordinary case and is
  explicitly permitted.
  MAY differ. A requester may submit a request on behalf of a distinct
  grantee.

Approver (approvedByUserId):
  MUST differ from the requester. MUST differ from the grantee. Both
  conditions hold with no exception, regardless of whether requester and
  grantee are the same person or different people. Concretely: a person
  may request elevation for themselves, but no person — including that
  same requester/grantee — may approve their own request. Self-approval
  is prohibited without exception in M37.

Revoker (revokedByUserId):
  Not required to be globally distinct from the requester, grantee, or
  approver. See Decision 12 for who is authorized to revoke and why no
  distinctness requirement applies to revocation.
```

No risk tier, capability, or condition of any kind waives the
approver-separation rule during M37 — the readiness assessment's own
"low-risk self-approval tier" question (raised as an open alignment
question) is resolved by this decision: **no such tier exists in M37.**
Risk-tier variation, richer approval routing, and any self-approval
exception for a defined low-risk case are explicitly deferred to M38,
consistent with `GD-M36-1` Decision 19's assignment of "second-approval
requirements, and self-approval restrictions" refinement to M38.

The approver-separation rule is enforced at the service layer
(application-level check before any state transition to
`APPROVED`/`DENIED` is persisted); a database-level `CHECK` constraint
comparing the `approvedByUserId` column against both `requestedByUserId`
and `granteeUserId` for inequality is also recommended where the target
Postgres version supports it cleanly, as defense in depth. No such
constraint applies to `revokedByUserId`, which may legitimately equal any
of the other three actor columns.

## Decision 10 — Grantable-Capability Allowlist (Appendix A)

M37's grantable-capability allowlist is **explicitly enumerated in this
decision** (Appendix A below) and consists of exactly four capabilities,
each copied verbatim from the live `apps/api/src/identity/permissions.catalog.ts`
`CAPABILITIES` constant, independently re-verified present in
`CAPABILITY_ROLE_MAPPINGS` at authorization time. **The M37 allowlist does
not include all 62 M36 capabilities, does not introduce any new
capability, does not rename any capability, and does not include any of
the four M36 reserved-but-unseeded capabilities**
(`employees:terminate`, `users:deactivate`, `users:assign-role`,
`offers:rescind`). No capability outside Appendix A's list may ever be
inserted into an `ElevationSessionCapability` row — this is enforced at
the service layer against a hard-coded allowlist constant, not against the
full 62-entry catalog.

M37 does not expand, seed additional rows into, or otherwise modify the
M36 `Permission`/`RolePermission` tables or the 62-permission/175-mapping
catalog. The allowlist is a *read-only reference* to four already-seeded
rows.

**Data sensitivity classification (binding, corrects an earlier
overstatement):** three of the four allowlisted capabilities
(`USERS_CREATE`, `USERS_READ`, `USERS_UPDATE`) operate on the `User`
model's account identity data — first/last name, email address, account
status, and role assignment. This is genuine, sensitive
security-administration data, verified via
`apps/api/src/users/users.controller.ts`'s `toResponseShape()`
(`id`, `firstName`, `lastName`, `email`, `status`, `roles`, `createdAt`,
`lastLoginAt` — `passwordHash` is confirmed excluded from every response).
**This decision does not claim, and no future document may claim, that
this data is non-sensitive.** It remains subject to the same tenant
scoping and least-privilege treatment as every other capability in the
M36 catalog. What these three capabilities do **not** do — verified by
inspecting the `User` Prisma model and every M37-relevant controller — is
create, modify, or expose any `Employee` or `Candidate` record: the
`User` model carries no field or relation referencing either, and
`toResponseShape()`'s field list contains no HR or recruiting data of any
kind. The fourth capability, `ROLES_ASSIGNABLE_READ`, is categorically
different: verified via `UsersService.getRoles()`
(`prisma.role.findMany({ select: { id: true, name: true } })`), its
response contains only platform role identifiers and names — no personal,
account-identity, employee, or candidate data of any kind. Appendix A
states this distinction precisely for each of the four capabilities; none
of the four is described as having "no PII" in an unqualified sense.

## Decision 11 — Expiration Validity Rules

`expiresAt` is mandatory once a session reaches `ACTIVE`, and elevation is
never indefinite. **No scheduler is required for secure expiration, and
none is authorized or assumed by this decision.** Any future authorization
consumer (none exists in M37 — see Decision 17) must, at the moment it
considers honoring an elevation, evaluate the complete validity predicate:

```text
status = ACTIVE
  AND tenantId matches the acting request's tenant
  AND now() >= startTime (activatedAt, or an explicit start time if one
       is later added)
  AND now() < expiresAt
  AND revokedAt IS NULL
  AND the specific capability being checked has a corresponding
       ElevationSessionCapability row with decision = GRANTED
```

A future scheduler MAY later reconcile a persisted `status` from `ACTIVE`
to `EXPIRED` for reporting, dashboarding, or maintenance convenience, but
**no future authorization decision may ever depend on that scheduler
having run.** The predicate above must be the sole source of truth for
validity at evaluation time, always re-derived from `expiresAt` and
`revokedAt` directly. M37 itself implements and tests this predicate as a
pure function; M37 does not call it from anywhere in the runtime
authorization path, because no such call site is authorized in M37
(Decision 17).

## Decision 12 — Revocation and Terminal-State Behavior

Revocation (`ACTIVE → REVOKED`) requires `revokedByUserId` and
`revokedReason`, is available at any point during `ACTIVE` regardless of
remaining time before `expiresAt`, and is itself a terminal, immutable
transition.

**Who may revoke (Decision 9):** the `revokedByUserId` actor is not
required to be globally distinct from the session's other actor columns.
Three cases are all explicitly permitted:

```text
Grantee self-revocation:
  The grantee may voluntarily relinquish or request revocation of their
  own elevation — revokedByUserId equals granteeUserId.

Requester-initiated revocation:
  The original requester may revoke a session they requested —
  revokedByUserId equals requestedByUserId (which may itself equal
  granteeUserId, per Decision 9).

Independently authorized revocation:
  A separate actor authorized to manage elevation sessions (exact
  authorization mechanism is an implementation-time detail within this
  decision's internal-service-only boundary — Decision 4) may revoke a
  session regardless of their relationship to the requester, grantee, or
  approver.
```

**Cancellation and revocation are distinct lifecycle actions and must
never be conflated:** `CANCELLED` (Decision 6: `REQUESTED → CANCELLED`) is
available only before any approval decision is recorded, is initiated by
the requester withdrawing their own pending request, and carries no
`revokedByUserId`/`revokedReason`. `REVOKED` (`ACTIVE → REVOKED`) is
available only after activation, carries `revokedByUserId` and
`revokedReason`, and follows the who-may-revoke rules above. No
implementation may use `CANCELLED` to represent a post-activation action or
`REVOKED` to represent a pre-approval withdrawal.

All terminal states (`DENIED`, `CANCELLED`, `EXPIRED`,
`REVOKED`, `ACTIVATION_FAILED`) are immutable — no service method may
mutate a row once it reaches a terminal state; a new `ElevationSession`
request is required to request elevation again after any terminal outcome
(Decision 8's uniqueness rules and Decision 13's concurrency rule apply
identically to the new request).

## Decision 13 — Tenant-Scoped Idempotency and Concurrency Controls

`idempotencyKey`, where supplied, is unique **within `tenantId`** via a
compound uniqueness constraint on `(tenantId, idempotencyKey)` — never a
single globally-unique column, which would be an unnecessarily broad
constraint for a tenant-isolated system and (per SEC-003 discipline)
inappropriate.

**Concurrency rule:** at most one non-terminal `ElevationSession`
(`status` in `REQUESTED`, `APPROVED`, or `ACTIVE`) may exist per
`(tenantId, granteeUserId)` pair at any time. This is recommended to be
enforced by a partial unique index defined in migration SQL (not
`@@unique` in `schema.prisma`), following the exact established idiom
`Offer`'s "one active offer per application" rule already uses
(`apps/api/prisma/schema.prisma:581-584`; SQL in
`20260630100000_m18b_offers/migration.sql`). A concurrent second request
for an already-non-terminal grantee must fail deterministically at the
database layer, not merely be discouraged at the service layer, closing
the race window `users.service.ts`'s own Last-SA guard comment
(`GD-M27-1` D5) already treats as a first-class concern in this codebase.

`APPROVED → ACTIVE` activation failure (`ACTIVATION_FAILED`) covers the
case where this concurrency guarantee itself is violated at the moment of
activation (e.g., a second session for the same grantee reached `ACTIVE`
first) — a deterministic, testable, terminal outcome rather than a silent
overwrite.

## Decision 14 — Strict Elevation Audit-Write Behavior (Narrow Exception)

Every `ElevationSession` lifecycle transition (request, approval, denial,
activation, expiration-detection where recorded, revocation, cancellation,
activation failure) must be recorded as an audit event using a **strict,
transaction-aware write path** such that the state transition and its
audit event either both succeed or both fail together — the transition
must never be persisted if its corresponding audit event cannot be
written.

This is a **narrow, named exception** for `ElevationSession` transitions
only. It must not silently change the existing, platform-wide behavior of
`AuditService.logEvent()`, which remains exactly as implemented today
(write-only, best-effort, failure-swallowing per AUD-1300) for every
existing caller. The implementation task is authorized to add a new,
separate strict method or transaction-aware mechanism (exact name and
signature to be finalized at implementation time — e.g. a method invoked
from within the same `$transaction` the state mutation uses, following
`users.service.ts`'s own `$transaction`-scoped pattern) alongside the
existing `logEvent()`, without modifying `logEvent()`'s signature,
behavior, or any of its current call sites.

**This exception does not satisfy, replace, or partially credit any part
of M39.** Audit reads, the viewer, filtering, actor/action/result/resource
correlation, tamper detection, retention enforcement, and failed-write
observability/recovery all remain M39 prerequisites in full, entirely
unaddressed by this narrow write-path exception. This decision governs
only how one write happens, not whether that write (or any other audit
record) can later be read, searched, verified as untampered, or retained
per policy.

## Decision 15 — Actor References and Referential Integrity

Grounded in the verified evidence in Decision 3/Background — no `User`
hard-delete path was found in the inspected user-management application
logic; account deactivation is a `status` transition
(`ACTIVE`/`SUSPENDED`/`DEACTIVATED`, with `DEACTIVATED → ACTIVE`
reactivation permitted) that preserves the row — `requestedByUserId`,
`granteeUserId`, `approvedByUserId`, and `revokedByUserId` are each named
actor references (Decision 9's separation rules govern which of these may
coincide). Because no application-level hard-delete of `User` was found,
and because `ElevationSession` rows are security-history records whose
integrity must never depend on a future, currently-unplanned change to
`User` deletion behavior, this decision recommends the same defensive
pattern
`audit.audit_events` already uses: actor-reference columns carry **no
cascading-delete foreign-key relationship** to `User` (plain UUID
reference, optionally a non-cascading/restrict-only FK if referential
integrity enforcement is desired at implementation time — the specific
choice between "plain UUID, no FK" and "FK with `onDelete: Restrict`" is
an implementation-time decision within this constraint, not fixed here).
**No implementation may add `onDelete: Cascade` on any actor-reference
column in this model, under any circumstance.**

## Decision 16 — Step-Up Authentication Limitation

The repository has no genuine MFA or step-up authentication mechanism
today (Decision 3/Background). M37 must not implement one, and must not
claim one exists. The `stepUpAuthMethod` and `stepUpVerifiedAt` fields
(Decision 8) are:

```text
Nullable — no NOT NULL constraint of any kind
Service-owned — never accepted as client-controlled input on any request
  M37 does not expose (and M37 exposes no request surface at all —
  Decision 4)
Required to remain null on every record created during M37 — no seed
  data, test fixture, or code path may populate a non-null value during
  M37's own implementation and validation
Prohibited from being treated as proof of verification by any code,
  anywhere, at any time — a non-null value in a future milestone must
  never be trusted as step-up evidence merely because the column is
  populated; a future, separately governed authentication milestone must
  define what a trustworthy value looks like and how it is produced
  before these fields carry real meaning
```

**Explicitly prohibited as substitute step-up evidence, now or in any M37
test:** password re-entry, a client-side confirmation dialog, a test
sentinel treated as if it were real, a manually supplied value, or any
other mechanism that creates the *appearance* of step-up authentication
without a trustworthy, separately governed verification mechanism behind
it.

## Decision 17 — Proof That Elevation Cannot Affect Runtime Authorization

`RolesGuard` remains the sole runtime authorization authority throughout
M37, unmodified. `CapabilityGuard` remains registered for dependency
injection only and unregistered on every controller, global guard
provider, and bootstrap path, unmodified. `JwtStrategy.validate()` and
`AuthService`'s token-issuance logic are unmodified — no elevation field
is read by, written to, or referenced from either. **No guard, strategy,
token service, controller, or authorization resolver anywhere in this
codebase may consult `ElevationSession` or `ElevationSessionCapability`
records during M37.** The implementation task must include a structural
test (mirroring `capability-parity.spec.ts`'s own metadata-drift-guard
technique) proving that no import chain connects `ElevationSessionService`
to `RolesGuard`, `CapabilityGuard`, `JwtStrategy`, or `AuthService` — not
merely a behavioral test that happens not to exercise such a path.

## Decision 20 — Meaning of "Active" in M37 (Binding Terminology Rule)

The lifecycle (Decision 6) contains an `ACTIVE` state for modeling and
testing purposes. This decision draws, and binds every future document
and implementation to, a strict distinction:

```text
Lifecycle-active elevation record:
  An ElevationSession row whose status column currently reads ACTIVE.
  This is a data-modeling fact about one row in one table. It has no
  reader, no consumer, and no effect on any request processed by this
  application during M37.

Authorization-effective grant:
  A real, runtime change to what a real request is permitted to do.
  Nothing in M37 produces this. No milestone before its own, separately
  governed activation decision produces this — and that activation
  decision cannot be granted before M39 is operational, per GD-M35-1
  Decision 4.
```

**During M37, an `ACTIVE` record is never authorization-effective.** No
governance document, code comment, test name, log message, or future
summary produced under this decision's scope may use the word "active" or
"activation" in a way that implies a user has received, gained, or been
granted additional real access. Where ambiguity is possible, "lifecycle-
active (not authorization-effective)" is the required phrasing.

## Decision 21 — M39 Activation Prerequisite

Per `GD-M35-1` Decision 4, elevation may be **built** (M37) before the
audit prerequisite (M39) is complete, but must not be **activated for
production use** until M39 is operational — an elevation mechanism without
a working, reviewable audit trail is a net new risk, not a safety
improvement, over today's permanent System Administrator role. M39's
specification (`governance/M35-COMMAND-CENTER-BLUEPRINT.md` Section 12)
requires a tenant-scoped audit-read API, a permission-controlled viewer,
filtering/search, approval-and-execution correlation, tamper-detection
controls, retention enforcement, and observability/recovery for failed
audit writes — none of which exists today, and none of which Decision 14's
narrow strict-write exception substitutes for or partially satisfies.

**Any future activation of elevated access — of any kind, under any
condition or environment — requires all three of the following, together:**

```text
1. A trustworthy step-up authentication mechanism (Decision 16) — no
   mechanism exists today, and M37 implements none; a future,
   separately governed authentication milestone must provide one before
   the stepUpAuthMethod/stepUpVerifiedAt fields carry real meaning.
2. M39's audit prerequisite confirmed operational (this Decision 21).
3. Its own explicit, separate governance decision authorizing activation
   specifically — not implied, inherited, or assumed from GD-M37-1, M39,
   or any step-up milestone's own completion individually.
```

This decision does not pre-authorize that future activation decision, does
not constrain its content beyond these three prerequisites, and does not
itself bring that activation any closer than "the foundation it would need
exists and is tested." Until all three are satisfied, an M37
`ElevationSession` in the `ACTIVE` lifecycle state remains, and must
remain, a modeled data fact with zero effect on any real request — see
Decision 20.

## Decision 22 — Relationship to M38 and Later Milestones

M37 does not authorize M38, M39, M40, or M46, or any other later
milestone's implementation — each requires its own separate governance
decision, exactly as this decision was required for M37. Specifically
deferred to M38 (per `GD-M36-1` Decision 19's existing, unedited
assignment): department scope, decision-case scope, second-approval-count
requirements beyond this decision's single-approver rule (an approver
strictly different from both requester and grantee — Decision 9), and any
self-approval exception for a defined low-risk tier. This decision's own
rule that a requester may equal a grantee (Decision 9) is settled by
GD-M37-1 itself and is not among the items deferred to M38. M38's own
governance decision must not assume the deferred items above are
pre-approved by this document — each is a fresh decision to be made when
M38 is drafted, informed by (not bound by) the groundwork this decision
lays.
