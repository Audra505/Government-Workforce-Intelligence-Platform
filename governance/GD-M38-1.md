# Background

## Why This Decision Exists

`GD-M35-1` identified that consequential workforce decisions today are
recorded, if at all, as bare status-string transitions with no captured
approver identity, no immutable decision history, and no maker-checker
enforcement beyond a coarse role-list narrowing. `Offer.approveOffer()`
(`offer.service.ts:453-495`) is the clearest example: it checks only that
the offer's `status` is `PENDING_APPROVAL` and that the caller holds
`System Administrator` or `HR Director`; it never records who approved it
distinctly from who submitted it, and nothing prevents the same individual
from creating, submitting, and approving the same offer. `GD-M36-1`
Decision 19 already named M38 as the milestone that builds the "reusable
Decision Case and Approval Foundation" this gap requires. M38 is that step,
scoped as narrowly and safely as verified repository evidence allows, and
explicitly forbidden from having any effect on a real business action or
runtime authorization decision until later, separately governed milestones
build the execution, audit-read, and activation layers this foundation
requires before real use.

## What the Readiness Assessment and Project-Owner Review Confirmed

Direct, repeated re-inspection of the running codebase (not reliance on
prior summaries) established the following facts, which this decision
treats as authoritative:

- No `DecisionCase`, `ApprovalRequest`, `ApprovalDecision`, `EvidenceItem`,
  `DecisionCaseRiskTrigger`, `PolicyEvaluation`, `ActionExecution`,
  `VerificationResult`, `AIRecommendation`, or `AgentRun` entity, service,
  or controller exists anywhere in `apps/api/src` or `apps/api/prisma`
  (repo-wide grep, zero matches outside governance documents).
- `Offer.approveOffer()` (`offer.controller.ts:359`,
  `offer.service.ts:453-495`) narrows the caller's role set
  (`System Administrator`, `HR Director` — Recruiter excluded) but performs
  no maker-checker check: no field on `Offer` records the approver's
  identity, and no code compares it to the submitter's.
- `hire.controller.ts:59` enforces `@RequireRoles('System Administrator',
  'HR Director')`, confirmed still in conflict with `directives/10`
  RBAC-701 ("Hiring Manager, HR Director"), confirmed still unresolved,
  confirmed test-guarded as intentional current behavior
  (`apps/api/test/hire.e2e-spec.ts:555`).
- `Compliance Officer` holds exclusively read-only capabilities across

## Decision 5 — Normalized Entity Boundary

M38 authorizes exactly these seven normalized entities:

```text
DecisionCase
EvidenceItem
DecisionCaseRiskTrigger
ApprovalRequest
ApprovalRequirement
ApprovalDecision
ApprovalRequestEvidence
```

No other table is created by this decision. `ApprovalRequirement` and
`ApprovalDecision` are deliberately **separate** entities — an
`ApprovalRequirement` is an immutable approval slot established when an
`ApprovalRequest` is created (it may remain unanswered; it is never itself
a decision), and an `ApprovalDecision` is created only when a human
actually acts, is append-only, and is immutable from creation (Decision
9). This is a deliberate departure from `GD-M37-1` Decision 8's
`ElevationSessionCapability` idiom, which correctly folds requirement and
decision into one mutable-until-decided row for a simpler, single-item
capability grant — M38's approval decisions carry materially more
audit-significant detail per event (reason, qualification snapshot,
evidence-version reference) and must never be edited in place, even before
a terminal state is reached, so a separate append-only child entity is
required instead of reusing M37's exact shape unmodified.

Full field-level specification of all seven entities is in Appendix A.

**Explicit deferral of other `GD-M35-1`-listed entities.** `GD-M35-1`
Decision 15 planned a broader M38 entity list — `PolicyEvaluation`,
`ActionExecution`, `VerificationResult` — and the blueprint's Section 9
lifecycle additionally contemplates `AIRecommendation`/`AgentRun`-style
AI-prepared inputs. The M38 readiness assessment identified tension
between that planned list and the narrower, practical foundation
verified repository evidence supports today. This decision resolves that
tension explicitly, refining M38's sequencing without removing any of
these capabilities from the broader target architecture:

```text
PolicyEvaluation      — deferred to M42 (Deterministic Policy Guard).
                         No table, no placeholder, no unconsumed
                         policyEvaluationId column anywhere in M38
                         (Decision 14).
ActionExecution        — deferred to a later, separately governed
VerificationResult       execution/verification milestone (not yet named
                         in the roadmap beyond M43's Command Center
                         framing). No table, no placeholder, no dangling
                         decisionCaseId-shaped reservation column on any
                         M38 entity for either.
AIRecommendation       — deferred to M44/M45 (LLM Shadow Mode; Governed
AgentRun                 Runtime LLM Integration). No table, no
                         placeholder, no reserved column.
```

**No placeholder table and no dangling reference column is created for
any of the five.** The forward-reference principle this decision applies
uniformly: a later entity holds the reference to an earlier one (exactly
as `ElevationSession.decisionCaseId`, Decision 15, is added now, by M38,
rather than M37 having had to pre-reserve a slot for a case it could not
have known about) — never the reverse. When M42, the execution/
verification milestone, or M44/M45 are eventually authorized, each adds
its own additive reference column pointing back at `DecisionCase`,
`ApprovalRequest`, or `EvidenceItem` as needed, without requiring any
change to this decision's tables.

## Decision 6 — Decision Case Subject References

`DecisionCase` subject references use a governed `DecisionCaseSubjectType`
enum, never a free-form string:

```text
DecisionCaseSubjectType:
  OFFER
  APPLICATION
  EMPLOYEE
  ELEVATION_SESSION
  GENERAL
```

Enumerated only because each is justified by an existing repository
entity (`Offer`, `Application`, `Employee`) or the M37 elevation model
(`ElevationSession`); `GENERAL` is the explicit no-record case type for a
decision case that does not correspond to any existing row (e.g., a
process-level or policy-level decision with no single subject record).

```text
GENERAL           → subjectId MUST be null
OFFER/APPLICATION/EMPLOYEE/ELEVATION_SESSION → subjectId MUST be non-null
```

Because a true polymorphic database foreign key spanning multiple,
differently-schema'd tables is unavailable in this codebase's multiSchema
Prisma setup, `subjectId` is a plain UUID column with **no** database
foreign key — mirroring `AuditEvent`'s own `entityType`/`entityId`
precedent. Referential integrity is instead enforced by a **deterministic
internal subject resolver**, invoked at `DecisionCase` creation time only,
which must:

```text
Validate that subjectType is one of the enumerated values
Verify the referenced subject row actually exists
Verify the subject row's tenantId matches the DecisionCase's own tenantId
Reject any unsupported subjectType or any cross-tenant reference
Fail closed — a resolver failure or a not-found subject blocks case
  creation; it is never treated as valid by omission
```

**This is a controlled, service-enforced polymorphic reference, not
database-enforced referential integrity.** No future document or code may
describe it as database-validated. This mirrors, and is grounded in the
same reasoning as, `GD-M37-1` Decision 15's actor-reference design and the
`assertActorInTenant` pattern it established.

## Decision 7 — Decision Case Lifecycle

`DecisionCase.status` is a governed enum limited to exactly:

```text
OPEN               — initial state; case exists, evidence may be attached,
                       no ApprovalRequest yet created
AWAITING_APPROVAL   — an ApprovalRequest now exists and is PENDING
NEEDS_INFORMATION   — a reviewer returned the active ApprovalRequest for
                       revision; the case awaits resubmission
APPROVED            — terminal; every ApprovalRequirement on the winning
                       ApprovalRequest version reached GRANTED
REJECTED            — terminal; any ApprovalRequirement on the active
                       ApprovalRequest reached REJECTED
CANCELLED           — terminal; the initiator withdrew the case before any
                       ApprovalRequirement was decided
```

**M38 does not create literal states for `DETECTED`, `AI_PREPARED`,
`POLICY_CHECKED`, `EXECUTED`, `VERIFIED`, or `CLOSED`.** `AI_PREPARED` and
`POLICY_CHECKED` have no writer in M38 (no AI, no Policy Guard — Decision
5's explicit `PolicyEvaluation`/AI deferral, Decision 20's AI/HIL
boundary); implementing them as literal enum values nothing ever sets
would be a misleading state implying unavailable functionality had
occurred. `EXECUTED` and `VERIFIED` belong to a later, separately governed
execution/verification milestone's own entity, not to `DecisionCase` —
see Decision 5's explicit `ActionExecution`/`VerificationResult`
deferral. `CLOSED` is not implemented as a distinct state from
`APPROVED`/`REJECTED`/`CANCELLED` in M38 because nothing in M38
distinguishes "approved" from "approved and fully closed out" — that
distinction only becomes meaningful once a real execution/verification
layer exists to close the loop, at which point a future milestone may
introduce it without rewriting M38's own history (Decision 5).

`APPROVED`, `REJECTED`, and `CANCELLED` are **terminal and immutable** in
M38 — no service method may mutate a `DecisionCase` row once it reaches
one of these three states. **An `APPROVED` case remains pending any
separately governed future execution process** — reaching `APPROVED`
never executes or authorizes a business action, and a future execution
entity (not built by M38) references `decisionCaseId` from its own table
rather than `DecisionCase` gaining new post-approval states.

## Decision 8 — Approval-Request Lifecycle and Versioning

`ApprovalRequest.status` is a governed enum limited to exactly:

```text
PENDING     — active; one or more ApprovalRequirement rows remain
               undecided
APPROVED    — terminal; every ApprovalRequirement reached GRANTED
REJECTED    — terminal; any ApprovalRequirement reached REJECTED
NEEDS_INFORMATION — terminal for this version; any ApprovalRequirement
               reached NEEDS_INFORMATION
SUPERSEDED  — terminal; this version was replaced by a newer
               ApprovalRequest on the same case (resubmission or
               elevated-risk escalation)
CANCELLED   — terminal; the case was cancelled while this request was
               still PENDING
```

**A `DecisionCase` may have only one active `PENDING` `ApprovalRequest` at
any time** (Decision 16's concurrency rules). Each `ApprovalRequest`
represents **one complete, immutable approval plan for one case version**:
every required Tier 1, Tier 2, and (where triggered) Tier 3
`ApprovalRequirement` for that version exists inside that **single**
request — **M38 never creates a separate, simultaneous Tier 3
`ApprovalRequest`** (Decision 11).

**Resolution rules:**

```text
All required ApprovalRequirement rows reach GRANTED
  → ApprovalRequest.status = APPROVED, DecisionCase.status = APPROVED

Any required ApprovalRequirement row reaches REJECTED
  → ApprovalRequest.status = REJECTED, DecisionCase.status = REJECTED
  (fail-fast: remaining PENDING requirements are not waited on, and no
   fabricated decision row is created for them)

Any required ApprovalRequirement row reaches NEEDS_INFORMATION
  → ApprovalRequest.status = NEEDS_INFORMATION,
    DecisionCase.status = NEEDS_INFORMATION
  (fail-fast, identically)
```

**Elevated-risk discovery after an approval request begins:** if a
`DecisionCaseRiskTrigger` (Decision 12) is recorded after a `PENDING`
`ApprovalRequest` already exists, the service must:

```text
1. Mark the current ApprovalRequest SUPERSEDED (its ApprovalRequirement
   and ApprovalDecision rows are preserved, unchanged, forever)
2. Create a new ApprovalRequest version (incremented version number,
   supersedesRequestId pointing at the prior version)
3. Populate the complete new requirement set for the new version,
   INCLUDING the newly required Tier 3 requirement
4. Freeze a new ApprovalRequestEvidence set for the new version
   (Decision 14) — the evidence set is never silently carried over
   unfrozen
5. Require entirely new ApprovalDecision rows against the new version's
   requirements — prior decisions are never copied, reused, or silently
   carried into the new version, even if the same individual would
   satisfy the same category again
```

**Resubmission after `NEEDS_INFORMATION` follows the identical
supersede-and-recreate procedure** — a new `ApprovalRequest` version, a
frozen new evidence set, and entirely new decisions required. **Old
requests, requirements, decisions, and evidence-set snapshots remain
immutable forever** — supersession never edits or deletes a prior version.

The version chain is explicit: `ApprovalRequest.version: Int` (starting at
1, monotonically increasing per case) plus `supersedesRequestId: String?`
(self-relation, nullable, populated only on versions 2+).

## Decision 9 — ApprovalRequirement and ApprovalDecision: Separate, Immutable, Append-Only

**`ApprovalRequirement`** — one immutable row per required approval slot,
created in full when its parent `ApprovalRequest` is created (never
created afterward, mirroring `GD-M37-1` Decision 8's "all rows created in
the same request-time operation" rule for `ElevationSessionCapability`).
Each row records:

```text
requiredAuthorityCategory   — governed enum (Decision 13)
requiredCapability          — nullable reference to an existing M36
                                Permission, populated only for
                                ACTION_AUTHORITY requirements (Decision 11)
sequenceOrder               — nullable ordering hint, where a future tier
                                design requires sequential (not merely
                                parallel) satisfaction; unconsumed by any
                                M38 ordering logic beyond display/audit
                                purposes unless Decision 11 specifies
                                otherwise for a given tier
tier                        — governed enum: TIER_1, TIER_2, TIER_3
approvalRequestId           — parent reference (real FK, same schema)
createdAt
```

A requirement **may remain unanswered** (no `ApprovalDecision` row
referencing it yet) — this is a normal, non-terminal state, not itself a
decision. `ApprovalRequirement` rows are never updated after creation.

**`ApprovalDecision`** — created **only** when a human actually acts.
**It must not have a `PENDING` decision value and must never be created in
a `PENDING` state.** Allowed decision outcomes are limited to exactly:

```text
GRANTED
REJECTED
NEEDS_INFORMATION
```

Each `ApprovalDecision` row is **append-only and immutable from the moment
it is created** — no service method may update an existing decision row,
under any circumstance, including from one valid value to another.
**A requirement may have at most one effective decision within one
approval-request version** — enforced by a database uniqueness constraint
on `(approvalRequirementId)` scoped to non-superseded rows (in practice, a
requirement belongs to exactly one, immutable `ApprovalRequest` version,
so at most one `ApprovalDecision` may ever reference a given
`approvalRequirementId` at all; Decision 16 specifies the exact
constraint).

Each decision must record:

```text
approvalRequirementId   — the exact requirement it answers (real FK)
decidedByUserId         — the deciding human (plain UUID, no FK — actor-
                            reference idiom, Decision 15/GD-M37-1
                            precedent)
decision                — GRANTED | REJECTED | NEEDS_INFORMATION
reason                  — mandatory text
qualificationSnapshot   — immutable text capture of what qualified this
                            actor at decision time (Decision 13)
evidenceSetVersion      — reference to the exact ApprovalRequestEvidence
                            freeze considered (Decision 14)
decidedAt               — timestamp
```

## Decision 10 — Case Initiation Versus Preparation

`DecisionCase` models two distinct actor references, never assumed
equivalent:

```text
initiatedByUserId   — who created or administratively recorded the case
preparedByUserId    — who substantively prepared the proposed action the
                        case represents
```

These **may** be the same person, but self-approval and separation rules
(Decision 11) must evaluate the **substantive preparer**
(`preparedByUserId`), never blindly treat every administrative case
creator as "the maker." A person who only administratively opened a case
on someone else's behalf, without substantively preparing the underlying
proposal, is not thereby disqualified from later approving it — only the
substantive preparer is subject to the preparer-separation rules below.
**AI or service identities may never satisfy a human approval
requirement** — `decidedByUserId` on every `ApprovalDecision` row must
resolve to a real, tenant-scoped `User` row via the same
`assertActorInTenant`-style check `GD-M37-1` established, and no
service-actor sentinel (e.g., an `AuditService.SYSTEM_USER_ID`-style
value) may ever pass that check (Decision 17).

## Decision 11 — Three Approval Tiers

### Tier 1 — Routine Single-Human Approval

Exactly one `ApprovalRequirement`, `tier = TIER_1`,
`requiredAuthorityCategory = ACTION_AUTHORITY`. **`ACTION_AUTHORITY` is
not a vague, unqualified category** — the requirement's `requiredCapability`
field must reference the exact existing M36 `Permission` row (from the
live 62-entry catalog, `permissions.catalog.ts`) that the decision type in
question requires, and qualification is checked against that specific
capability (Decision 13), never against a generic "any authorized user"
notion. **The Tier 1 approver must differ from the substantive preparer**
(`preparedByUserId`, Decision 10) — the person who only administratively
created the case may approve it, but only if that same person is not also
the substantive preparer of the proposed action.

### Tier 2 — Workforce Decision Owner Maker-Checker

Exactly two `ApprovalRequirement` rows, both `tier = TIER_2`:

```text
DEPARTMENT_OR_HIRING_AUTHORITY
HR_AUTHORITY
```

**These two requirements must be satisfied by two distinct humans — one
person may never satisfy both.** The substantive preparer
(`preparedByUserId`) **may** satisfy at most one of the two Tier 2
requirements, provided they are otherwise qualified for it; the other,
distinct human provides the checker separation this tier exists for. This
preserves the intended two-human model from `GD-M35-1` Decision 12 exactly
— it does not require a third approver merely because the preparer also
happens to hold one of the two qualifying authority categories. **Routine
final offers and hires do not require Independent Oversight Reviewer
approval by default** — Tier 3 is never a standing participant in Tier 2
decisions (`GD-M35-1` Decision 12's binding "additive, not interchangeable"
rule). **M38 only models this approval plan as reusable data and service
rules. M40 exclusively owns integration with the actual offer and hire
endpoints** (Decision 19 below) — M38 implements and tests the Tier 2
mechanism in isolation, never wired to `offer.service.ts` or
`hire.service.ts`.

### Tier 3 — Independent Oversight Reviewer

**Tier 3 is one additional `ApprovalRequirement` inside the same
`ApprovalRequest` version that already carries the case's Tier 1 or Tier 2
requirements — it never creates a separate, simultaneous `ApprovalRequest`**
(Decision 8). `requiredAuthorityCategory = INDEPENDENT_OVERSIGHT_REVIEWER`.
The reviewer satisfying this requirement must differ from:

```text
The substantive preparer (preparedByUserId)
The beneficiary or grantee, where the case has one (e.g., an
  ELEVATION_SESSION-subject case's granteeUserId, resolved via the
  subject resolver, Decision 6)
Every person who satisfied a Tier 1 or Tier 2 requirement on that same
  ApprovalRequest
```

Tier 3 applies only when a `DecisionCaseRiskTrigger` (Decision 12) has
been recorded against the case — it is never a standing requirement on an
ordinary case.

## Decision 12 — Elevated-Risk Triggers: Normalized, Append-Only, Never a Boolean

Elevated-risk conditions are represented as normalized, append-only
`DecisionCaseRiskTrigger` records — **M38 does not use a single
`requiresTier3` boolean column.** The governed trigger-type enum:

```text
DecisionCaseRiskTriggerType:
  COMPLIANCE_OR_POLICY_EXCEPTION
  FAILED_CONTROL_OVERRIDE
  PRIVILEGED_OR_EMERGENCY_ACCESS
  AUTHORIZATION_POLICY_OR_SECURITY_CONFIGURATION_CHANGE
  SELF_PREPARED_WORKFORCE_PLAN_OR_FORECAST_ACTIVATION
  SENSITIVE_BULK_ACTION
  OTHER_EXPLICITLY_CLASSIFIED
```

(directly enumerating `GD-M35-1` Decision 13's elevated-risk condition
list; `OTHER_EXPLICITLY_CLASSIFIED` exists only for a future, explicitly
governed addition — it is never used as a silent catch-all without an
accompanying `reason` explaining the specific classification).

Each trigger row records:

```text
triggerType         — the governed enum above
reason               — mandatory text
sourceOrProvenance   — HUMAN | DETERMINISTIC_SYSTEM (Decision 14's
                         provenance categories, reused here)
createdByUserId      — nullable, no FK (actor-reference idiom); null only
                         when sourceOrProvenance = DETERMINISTIC_SYSTEM and
                         no human actor is applicable
createdAt
caseVersion          — which ApprovalRequest version this trigger applied
                         to (or preceded, if it caused a new version)
includedInApprovalPlan — boolean; whether this trigger actually resulted
                         in a Tier 3 requirement on some ApprovalRequest
                         version (a trigger recorded after a case is
                         already terminal, for instance, is retained for
                         history but never acted upon)
```

**M38 does not detect these risks automatically.** Risk triggers may be
supplied **only** through the internal deterministic service, for
modeling and testing purposes — there is no rules-evaluator, no automatic
classification, and no inference from case content. **M42 (Deterministic
Policy Guard) owns automatic risk detection** in a later, separately
governed milestone; M38's contribution is exclusively the data model and
the service method that records a trigger and, where appropriate,
supersedes the active `ApprovalRequest` per Decision 8.

## Decision 13 — Authority Categories and Temporary Qualification

`AuthorityCategory` is a governed enum, stored on `ApprovalRequirement`
and referenced at decision time — legacy role names are never embedded
directly into the approval engine's schema or logic:

```text
AuthorityCategory:
  ACTION_AUTHORITY
  DEPARTMENT_OR_HIRING_AUTHORITY
  HR_AUTHORITY
  INDEPENDENT_OVERSIGHT_REVIEWER
```

**Temporary, migration-era qualification mapping (dormant M38 behavior and
tests only — not a claim that any future profile is active):**

```text
DEPARTMENT_OR_HIRING_AUTHORITY → current Hiring Manager role
HR_AUTHORITY                   → current HR Director role
INDEPENDENT_OVERSIGHT_REVIEWER → current Compliance Officer role
ACTION_AUTHORITY               → actor must hold a current legacy role
                                    whose live M36 CAPABILITY_ROLE_MAPPINGS
                                    entry grants the EXACT Permission
                                    referenced by the specific
                                    ApprovalRequirement.requiredCapability
                                    — never a role-name check alone
```

**These are temporary qualification mappings for dormant M38 behavior and
tests. They do not activate the future Workforce Decision Owner or
Independent Oversight Reviewer profiles.** `GD-M35-1` Decision 3 and
Section 6 of the blueprint remain the authoritative, still-unimplemented
design for those two profiles; this decision's mapping is a
service-layer, swappable resolver function only — analogous in spirit to
`permissions.catalog.ts`'s own `CAPABILITY_ROLE_MAPPINGS` table — never a
schema-level or permanent commitment. **`System Administrator` status must
not automatically satisfy `DEPARTMENT_OR_HIRING_AUTHORITY`, `HR_AUTHORITY`,
or `INDEPENDENT_OVERSIGHT_REVIEWER` merely because it is an administrative
role** — an actor must hold the specific mapped legacy role (or, for
`ACTION_AUTHORITY`, the specific mapped capability) to qualify, with no
implicit System-Administrator override of any kind.

**Each `ApprovalDecision` must snapshot what qualified the actor at
decision time** (`qualificationSnapshot`, Decision 9) — an immutable text
capture (e.g., the qualifying role name and/or capability key at the
moment of decision) — so historical meaning survives later role or
profile migration, exactly mirroring `GD-M37-1` Decision 15's rationale
for actor-reference design.

**Qualification is checked at two points:**

```text
1. When an actor is assigned to a requirement, if the implementation
   introduces an explicit assignment step (optional in M38 — a
   requirement may also simply await any qualifying actor's decision
   without a prior assignment record)
2. Mandatorily, at the moment the actor submits the decision — this check
   can never be skipped even if an earlier assignment-time check already
   passed
```

**A deactivated or no-longer-qualified actor cannot submit a new
decision** — the decision-time qualification check fails closed exactly
like `assertActorInTenant` does for M37. **An existing historical decision
is never retroactively erased or invalidated** by a later deactivation or
qualification change — the `qualificationSnapshot` preserves its meaning
permanently.

## Decision 14 — Evidence Model and Frozen Evidence Sets

**`EvidenceItem`** — append-only, case-scoped:

```text
tenantId, decisionCaseId
evidenceType              — governed enum (e.g. SOURCE_RECORD_REFERENCE,
                              HUMAN_NOTE, SYSTEM_DERIVED_SUMMARY)
sensitivityClassification — governed enum: USER_ACCOUNT_IDENTITY,
                              EMPLOYEE_CANDIDATE_PII, AGGREGATE_EXECUTIVE,
                              COMPLIANCE_SENSITIVE,
                              PRIVILEGED_ACCESS_EVIDENCE
sourceType, sourceId      — same governed-enum-plus-UUID, no-FK pattern as
                              DecisionCase.subjectType/subjectId (Decision
                              6), independently tenant-validated
provenanceType            — HUMAN | DETERMINISTIC_SYSTEM (exactly two
                              values in M38 — never AI; Decision 17)
producedByUserId          — nullable, no FK; populated only when
                              provenanceType = HUMAN
capturedAt                — timestamp
summary                   — optional, PII-minimized/redacted text; never
                              a copy of the full source record
integrityOrVersionMetadata — optional, where the source supports it (e.g.
                              a source record's updatedAt at capture time)
createdAt
```

**Do not copy full `Employee`, `Candidate`, `Application`, `Interview`,
`Offer`, or other sensitive source records into `EvidenceItem` rows, and
do not use uncontrolled JSON blobs for raw evidence.** The `sourceType`/
`sourceId` reference plus a short `summary` is sufficient; a future
reviewer receives only the minimized `summary`, gated by
`sensitivityClassification`-driven masking rules the implementation task
must define, never a raw join into the source table. **Do not label
deterministic system evidence as AI-generated** — `provenanceType =
DETERMINISTIC_SYSTEM` describes exactly what M38 itself, or a future
deterministic service (e.g., M42's Policy Guard), produces; it is never
relabeled `AI` regardless of how sophisticated the deterministic logic
becomes. **Do not use a service-actor sentinel as a human approver** — a
`DETERMINISTIC_SYSTEM`-provenance evidence item's absent `producedByUserId`
must never be reused, aliased, or repurposed to satisfy any
`ApprovalDecision.decidedByUserId` check (Decision 10, Decision 17).

**`ApprovalRequestEvidence`** — a normalized join table that **freezes**
the exact evidence set presented for one specific `ApprovalRequest`
version:

```text
approvalRequestId, evidenceItemId (composite unique — an item is included
  at most once per request version)
includedAt
```

**After submission:** existing `EvidenceItem` rows remain immutable;
adding a new `EvidenceItem` to the case does **not** silently alter an
already-`PENDING` `ApprovalRequest`'s frozen set (a new item is simply not
joined into an already-frozen `ApprovalRequestEvidence` set); materially
new evidence requires the supersession-and-new-version procedure (Decision
8) so that decisions remain traceable to the **exact** evidence set
considered at the time. **Do not add an unconsumed `policyEvaluationId`
placeholder anywhere** — no `PolicyEvaluation` entity exists in M38, and no
column may reference one that does not exist (Decision 5's explicit
`PolicyEvaluation` deferral; contrast with `GD-M37-1`'s own
`correlationId`, which this decision deliberately does not imitate here
because no consumer or governance basis for it exists at the evidence
level).

## Decision 15 — M37 Scope Extension

`ElevationSession` is extended additively with the following fields —
this is the only modification to an existing M37 table this decision
authorizes:

```text
decisionCaseId       String?  — nullable, no FK (mirrors every other
                                  actor/reference column on this table
                                  per GD-M37-1 Decision 15's established
                                  no-FK-to-security-history-adjacent-
                                  entities-unless-restrictive posture);
                                  correlates an elevation request to the
                                  DecisionCase that authorized or explains
                                  it
scopeType            ElevationSessionScopeType — governed enum, default
                                  TENANT
scopeDepartmentId    String?  — nullable; real, restrictive foreign key to
                                  organization.departments
scopeDecisionCaseId  String?  — nullable; real, restrictive foreign key to
                                  the new DecisionCase table
```

```text
ElevationSessionScopeType:
  TENANT
  DEPARTMENT
  DECISION_CASE
```

**Binding invariants (enforced at both the database and service layer):**

```text
scopeType = TENANT          → scopeDepartmentId IS NULL AND
                                scopeDecisionCaseId IS NULL
scopeType = DEPARTMENT      → scopeDepartmentId IS NOT NULL AND
                                scopeDecisionCaseId IS NULL
scopeType = DECISION_CASE   → scopeDecisionCaseId IS NOT NULL AND
                                scopeDepartmentId IS NULL
When scopeType = DECISION_CASE, the scope case (scopeDecisionCaseId) must
  match the session's own correlating case (decisionCaseId) unless a
  future governance decision explicitly documents a justified exception —
  this decision authorizes no such exception itself
All referenced Department and DecisionCase rows must belong to the same
  tenantId as the ElevationSession row referencing them
Scope is immutable after ElevationSession creation — no service method
  may change scopeType, scopeDepartmentId, or scopeDecisionCaseId once set
Scope can never be widened after creation, under any circumstance
Deletion of a Department or DecisionCase row must never cascade-destroy
  ElevationSession security history
```

**Real foreign keys, not a generic unvalidated UUID:** `Position.department`
and `Employee.department` (`schema.prisma:106,189`) already establish that
a real, cross-Postgres-schema Prisma `@relation` (in this case, `identity`
→ `organization` for `scopeDepartmentId`, and `identity` → the new M38
table's schema for `scopeDecisionCaseId`) with **no `onDelete` clause**
(Postgres's restrictive-by-default behavior, identical to every existing
FK in this schema) is structurally supported by this repository's existing
multiSchema Prisma configuration. Both new foreign keys use this exact,
already-proven idiom. **This decision does not need to invoke a
"real FK is impossible" exception** — it is not impossible here, and no
generic unvalidated UUID is used for either field.

**These additions remain authorization-inert.** They exist purely as
correlation and scope *data* on a dormant table. `GD-M37-1`'s
`isElevationLifecycleCapabilityValidAt()` (`elevation-session.service.ts:
309-320`) is **not modified** by this decision — it continues to ignore
`decisionCaseId`/`scopeType`/`scopeDepartmentId`/`scopeDecisionCaseId`
entirely, and no runtime authorization path is authorized to read them
either. M39 and a separate future activation governance decision
(`GD-M37-1` Decision 21) remain required, unaffected by this decision, before
any scoped elevation could ever become authorization-effective.

```text
                                    categories already exist on that

  requirement                      ApprovalRequirement belongs to exactly

No decision after terminal      — a decision attempt against an

                                    ApprovalRequest has already left

Real-database concurrency       — a future implementation task's
  tests required                   validation gate (Decision 21) must
                                    include tests against a real
                                    PostgreSQL instance proving the
                                    partial-unique-index and

Superseded versions immutable   — enforced identically to every other
                                    terminal-state immutability rule in

```

**This decision does not authorize a separate, simultaneous Tier 3
`ApprovalRequest` coexisting with the one-active-`PENDING`-request-per-case
constraint** — Tier 3, when triggered, is always folded into the single
active request version (Decision 8, Decision 11), never a second
concurrently-open request.

## Decision 17 — Approval Expiration: Explicitly Deferred

**M38 does not implement approval-request expiration.** No expiration
timestamp field, no scheduler, no timeout-driven reassignment, no
automatic rejection, and no reminder job of any kind is authorized by this
decision. This mirrors `GD-M37-1`'s own precedent of declining to
introduce scheduler infrastructure absent a concrete need — no scheduler,
cron, or background-worker mechanism exists anywhere in this codebase
today, and this decision does not introduce the first one. Approval
expiration remains deferred until a concrete business requirement and an
explicit owning milestone exist; it is not silently assumed to be part of
any specific future milestone by this decision.

## Decision 18 — Strict Audit-Write Behavior and the M39 Gate

Every M38 lifecycle transition listed below must be recorded via the
**same strict, transaction-aware audit-write path `GD-M37-1` Decision 14
introduced** (`AuditService.logEventStrict()`), such that the state
mutation and its audit event succeed or fail together:

```text
Case creation
Evidence attachment
Risk-trigger creation
Approval-request submission
Request supersession
Each approval decision
Needs Information
Case resubmission
Case approval
Case rejection
Case cancellation
```

This decision authorizes a new, additive set of `AuditEventType` enum
values for these events (exact names finalized at implementation time,
following the `ELEVATION_SESSION_*` naming convention `GD-M37-1` Decision
18 established). **This does not change `AuditService.logEvent()`'s
existing signature, behavior, or any of its existing call sites** —
`logEvent()` remains exactly as implemented today (write-only,
best-effort, failure-swallowing per AUD-1300) for every existing caller,
identically to how `GD-M37-1` Decision 14 protected it.

**M38 does not implement:**

```text
An audit-read API
An audit viewer
Filtering or search over audit records
Tamper-detection controls
Retention enforcement
Failed-write recovery
Audit observability of any kind
```

**M38 does not satisfy M39.** M39's full prerequisite (tenant-scoped
audit-read API, permission-controlled viewer, filtering, actor/action/
result/resource/timestamp visibility, approval-and-execution correlation,
tamper-detection, retention enforcement, and failed-write observability/
recovery) remains entirely unaddressed by this narrow write-path reuse,
identically to how `GD-M37-1` Decision 14 stated its own strict-write
exception does not satisfy any part of M39. **No Independent Oversight
Reviewer workflow, and no business-action execution deriving from an
`APPROVED` `DecisionCase`, may become operational before M39 and every
other required later gate is satisfied.**
