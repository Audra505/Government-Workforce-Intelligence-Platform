# Governance Decision: GD-M34-2
# Executive Dashboard Aggregate Expansion & Limited Non-Trend Visual Indicators

Project: AI-Driven Staffing Optimization Platform for Government HR

Decision ID: GD-M34-2

Status: Approved — Implementation Authorized

Date: 2026-07-27

Approved By: Repository Owner (implementation directive, this session)

Milestone Context:

M34 (`GD-M34-1`, implementation commit `0d0ef60`, CI-confirmed) shipped
`ExecutiveMetricsService` and `GET /api/v1/intelligence/executive-metrics`
with four aggregate metrics (Vacancy Rate %, Coverage Rate %, Time To
Fill, Hiring Velocity) and the `WorkforceSignalSnapshot` history
foundation. A follow-on implementation task requires the Executive User
dashboard to be rebuilt to match a product-owner-approved visual mockup
(`eu-dashboard-final-mockup.html`, artifact
`e6fd63bd-2961-4598-bb4f-d0522c806615`), which surfaces two additional
groups of tenant-wide counts — a "Workforce Snapshot" (Active Workforce,
Active Positions, Unfilled Vacancies, Critical Vacancies) and a "Last 30
Days Activity" panel (Hires, Separations, Vacancies Opened, Vacancies
Filled) — plus non-trend visual indicators (single-value progress bars
and ring gauges, none of them charts, sparklines, or historical
comparisons). None of the eight new counts, and none of the visual
treatment, was authorized by `GD-M34-1`. This decision authorizes both,
as a narrow, explicitly-scoped follow-on.

# Decisions

## Decision 1 — Relationship to GD-M34-1

This decision does not modify, relax, or reinterpret any `GD-M34-1`
decision. The four existing metrics (Vacancy Rate %, Coverage Rate %,
Time To Fill, Hiring Velocity), their formulas, confidence rules,
windows, and RBAC are unchanged. This decision adds two new result
groups to the same response body and authorizes a matching frontend
layout; it does not touch `WorkforceReadinessService`,
`AttritionRiskService`, `VacancyRiskService`, or `DepartmentGapService`.

---

## Decision 2 — New Aggregate Fields: Definitions

All eight counts are tenant-wide, point-in-time or fixed-30-day-window
aggregates computed directly via Prisma `count()` inside
`ExecutiveMetricsService` — no row is ever fetched into memory in
individually-identifiable form.

**Workforce Snapshot (point-in-time, no window):**

```text
activeWorkforce:
  Employee.count({ tenantId, deletedAt: null, employmentStatus: 'ACTIVE' })
  — identical filter the dashboard's existing "Active Workforce" KPI card
    uses for SA/HRD/WP (GET /employees?employmentStatus=ACTIVE)

activePositions:
  Position.count({ tenantId, deletedAt: null, status: 'ACTIVE' })
  — reuses ExecutiveMetricsService's existing totalActivePositionCount
    query verbatim (GD-M34-1 Decision 5) — zero marginal query cost

unfilledVacancies:
  Vacancy.count({ tenantId, deletedAt: null, status: { in: ['OPEN', 'IN_RECRUITMENT'] } })
  — reuses ExecutiveMetricsService's existing openVacancyCount query
    verbatim (GD-M34-1 Decision 5) — zero marginal query cost

criticalVacancies:
  Vacancy.count({ tenantId, deletedAt: null, priority: 'CRITICAL' })
  — identical filter the dashboard's existing "Critical Vacancies" KPI
    card uses for SA/HRD/WP (GET /vacancies?priority=CRITICAL)
```

**Last 30 Days Activity (fixed 30-day trailing window — a new governed
constant, `SNAPSHOT_ACTIVITY_WINDOW_DAYS = 30`, distinct from Decision
7's 365-day Time To Fill window and Decision 8's 90-day Hiring Velocity
window; a shorter, "recent activity" window is intentional and
consistent with GD-M34-1 Decision 8's rationale for choosing a
window shorter than Time To Fill's):**

```text
hires:
  Employee.count({ tenantId, deletedAt: null,
                    hireDate: { gte: windowStart, lte: now } })
  — identical filter the dashboard's existing Operational Snapshot
    "Active Workforce" chip uses for SA/HRD/WP

separations:
  Employee.count({ tenantId, deletedAt: null, employmentStatus: 'SEPARATED',
                    terminationDate: { gte: windowStart, lte: now } })
  — identical filter the dashboard's existing Operational Snapshot chip uses

vacanciesOpened:
  Vacancy.count({ tenantId, deletedAt: null,
                   createdAt: { gte: windowStart, lte: now } })
  — identical filter the dashboard's existing Operational Snapshot chip uses

vacanciesFilled:
  Vacancy.count({ tenantId, deletedAt: null,
                   filledAt: { gte: windowStart, lte: now } })
  — identical filter the dashboard's existing Operational Snapshot chip uses

windowDays: 30 (reported alongside the four counts, matching the
  windowDays convention GD-M34-1 Decision 10 established for Time To
  Fill / Hiring Velocity)
```

Every count is a plain non-negative integer, always defined — none of
these eight facts has an undefined-denominator case (they are not
ratios), so unlike Decisions 5/6/7 of `GD-M34-1`, none is ever `null`. A
count of 0 is a fully valid, fully confident answer, matching the
precedent `GD-M34-1` Decision 8 already established for Hiring Velocity.
No `confidence` field is attached to these eight counts — confidence
scoring exists in this platform's Intelligence layer to express formula
uncertainty (an undefined denominator, a thin sample), and none of these
eight values has any such uncertainty to express.

---

## Decision 3 — No New List Access for Executive User

This decision grants Executive User **zero** new access to
`EmployeeController`, `PositionController`, `VacancyController`,
`ApplicationController`, `InterviewController`, `OfferController`,
`CandidateController`, or `HireController`. Every one of the eight new
counts is computed by a dedicated `count()` query inside
`ExecutiveMetricsService` itself — the same aggregate-only construction
`AttritionRiskService` already uses (see that service's file-level
comment: "no employee row, name, or identifier is ever fetched into
memory"). Executive User continues to receive `403 Forbidden` from every
one of those list controllers, unchanged.

---

## Decision 4 — RBAC: Unchanged

`GET /api/v1/intelligence/executive-metrics` keeps the exact
`@RequireRoles('System Administrator', 'HR Director', 'Workforce
Planner', 'Executive User')` list `GD-M34-1` Decision 4 established.
Recruiter, Hiring Manager, and Compliance Officer remain forbidden from
this endpoint, unchanged. No new endpoint is created, so no new RBAC
surface exists to govern.

---

## Decision 5 — No Snapshot Persistence for the Eight New Counts

The eight new counts are **not** written to `WorkforceSignalSnapshot`,
and no new `signalType` value is added to the governed set `GD-M34-1`
Decision 15 defined. Rationale:

```text
These are explicitly "fixed current-period counts" per this task's own
  instruction — not a score or rate a future trend/forecast milestone
  would consume, unlike the four GD-M34-1 metrics (which already have a
  documented, if unrealized, forward path toward FR-412/FR-400).
Persisting eight additional daily rows per tenant, with no named
  consumer and no governance decision authorizing a read path for them,
  would repeat the exact anti-pattern GD-M34-1 Decision 14 was written to
  prevent — accumulating history "just in case" without a stated future
  use.
If a future milestone identifies a real need to trend Workforce Snapshot
  or Last 30 Days Activity, that milestone must independently justify
  and govern it, per GD-M34-1 Decision 18's re-verification requirement.
```

`SnapshotWriterService` is not called for any of these eight values.
`ExecutiveMetricsService.getByTenant()`'s existing four snapshot writes
(Decision 16-17 of `GD-M34-1`) are completely unchanged — still exactly
four writes per call, still the same four `signalType` values.

---

## Decision 6 — No Suppression Rule Required

`GD-M33-1` Decision 6 introduced a Minimum Headcount Suppression Rule
because department-scoped aggregates can shrink to a population small
enough (n=1) to re-identify an individual. That risk does not apply
here: every one of the eight new counts (and all four `GD-M34-1`
metrics) is a **tenant-wide** aggregate, never department-scoped or
otherwise sliced. A tenant-wide count of 0, 1, or any other small number
reveals only a tenant-level fact ("this agency currently has 1 critical
vacancy"), not an individual's identity or status — the same reasoning
`GD-M34-1` Decision 20 already relied on to exclude department-level
breakdown of its four metrics outright rather than suppress it. No
suppression field, threshold, or `suppressed: true` flag is introduced
by this decision.

---

## Decision 7 — Visual Constraints (Frontend)

The Executive Dashboard body is rebuilt to match the approved mockup
under the following, explicitly governed, constraints:

**Permitted:**

```text
Ring gauges for Workforce Readiness / Attrition Risk — unchanged visual
  pattern from GD-M34-1's RingGauge component; the ring fills to the
  single current score, nothing else
Flat single-value progress bars for Coverage Rate / Vacancy Rate — a
  bar filled to the current percentage only, no marker, threshold line,
  target indicator, or comparison value drawn on it
A signed 30-day net-change chip on Workforce Snapshot tiles, computed
  directly from two of this decision's own counts in the same response
  (e.g., hires − separations) — arithmetic on already-real numbers, not
  a historical comparison; this is the identical pattern already shipped
  and governed for the SA/HRD/WP Operational Snapshot cards (see
  apps/web/src/app/(dashboard)/dashboard/page.tsx's formatNetChip)
```

**Prohibited (restated from GD-M34-1 Decisions 19-20 and this task's own
instruction, for a single point of reference on this page):**

```text
Trend lines, sparklines, or any chart with more than one data point
Prior-period deltas ("+3 vs last week") — the only permitted delta is
  the same-response net-change chip described above, which is not a
  comparison to a prior observation
Forecasting or any predictive output
Recommended headcount or any staffing recommendation
AI/LLM-generated predictions or narrative text
Alerts, a watchlist, or "top priority" recommendation cards
Row-level, department-level, or recruiting-domain detail of any kind
"Design mockup," "not live," "proposed," or dashed/concept styling on
  the production page — the mockup's own such markings (added for
  design-review purposes only) are not carried into the real dashboard
Oversized decorative illustrations
```

## Decision 10 — Supersession of GD-M34-1 Decision 12 (Dashboard Placement)

`GD-M34-1` Decision 12 originally placed a "Workforce Metrics" card (the
four `GD-M34-1` metrics: Vacancy Rate %, Coverage Rate %, Time To Fill,
Hiring Velocity) on the operational dashboard for System Administrator,
HR Director, and Workforce Planner, alongside Workforce Readiness,
Attrition Risk, and Vacancy Risk Signals.

This decision **supersedes that placement only**:

```text
Workforce Metrics is removed from the operational dashboard for System
  Administrator, HR Director, and Workforce Planner.
Workforce Metrics remains available in /intelligence for System
  Administrator, HR Director, Workforce Planner, and Executive User —
  unchanged (GD-M34-1 Decision 13).
Workforce Metrics remains central to the Executive User dashboard —
  Executive User has no operational-dashboard alternative, so this
  remains its only aggregate operating-metrics view.
No RBAC, formula, endpoint, or DTO field is removed. This is a
  dashboard-placement-only change: the underlying
  GET /api/v1/intelligence/executive-metrics response, its RBAC list,
  and every formula in GD-M34-1 Decisions 5-9 are unchanged.
```

Rationale: the four metrics were fully duplicated between the operational
dashboard and the `/intelligence` Workforce Signals tab, crowding a
dashboard surface intended to stay a quick operational overview
(Operational Snapshot, Workforce Intelligence signals, Vacancy Risk
Signals, Recruiting, open-vacancy context) with detail that already had a
dedicated home.

`GD-M34-1` Decision 12 is not edited or deleted — it remains the accurate
historical record of what M34 originally shipped. This decision records
the later placement change; `GD-M34-1` itself is unchanged.
