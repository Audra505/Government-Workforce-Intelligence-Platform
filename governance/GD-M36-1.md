# Background

## Why This Decision Exists

M35 established that hard-coded role-name authorization should eventually
become capability-based authorization, and that seeding the dormant
`Permission`/`RolePermission` tables is the natural first implementation
step. `apps/api/src/identity/roles.guard.ts`'s and `jwt.strategy.ts`'s own
code comments have anticipated this step since early in the project's
history (`jwt.strategy.ts:36`: *"Phase 2: add permission loading here if
per-request RBAC enforcement requires it."*). M36 is that step, scoped as
narrowly and safely as the repository's existing evidence allows.

## What the Corrected Assessment Confirmed

Direct, repeated re-inspection of the running codebase (not reliance on
prior summaries) established the following facts, which this decision
treats as authoritative:

- **70** production `@RequireRoles(...)` decorator occurrences exist across
  15 controller files (68 method-level, 2 class-level — `users.controller.ts`
  line 55, `roles.controller.ts` line 34).
- Those 70 decorators protect **73** distinct endpoint methods (68 from
  1:1 method-level decorators, plus 4 covered by `users.controller.ts`'s
  class-level decorator and 1 covered by `roles.controller.ts`'s).
- Those 73 endpoints resolve to exactly **7** unique legacy role-set
  combinations.
- `Permission` and `RolePermission` are schema-present and fully dormant —
  zero seeded rows, zero runtime queries anywhere in `apps/api/src`.
- No caching, revocation, or refresh-token infrastructure exists anywhere
  in the codebase; JWTs are stateless, self-contained, and valid for
  `JWT_ACCESS_EXPIRES_IN_SECONDS = 3600` (one hour) with no per-request
  database check.
- 22 backend unit spec files and 12 e2e spec files reference the seven
  role names directly; `platform-roles.spec.ts` is a dependency-free,
  authoritative enumeration test for the seven-role set.
- 30 frontend files derive access from `roles: string[]` read off the
  session; `platform-header.tsx` is the single centralized source of
  top-level navigation visibility.
- `users.service.ts` enforces `LAST_SYSTEM_ADMINISTRATOR` (a
  `$transaction`-scoped guard preventing a tenant from reaching zero active
  System Administrators) and `FORBIDDEN_ROLE_ASSIGNMENT` (HR Director may
  not assign the System Administrator role) — both role-name-based, both
  confirmed unaffected by this decision's scope.
- The hire endpoint (`apps/api/src/recruiting/hire.controller.ts:57`)
  enforces `@RequireRoles('System Administrator', 'HR Director')`, in
  conflict with `directives/10` RBAC-701 ("Hiring Manager, HR Director") —
  confirmed still present, still unresolved, still explicitly out of this
  decision's scope.

decision does not start, and must not be read as starting, any

`apps/api/prisma/seed.ts`'s `DEV_FIXTURE_USERS` array, `seedDevUser()`, and

## Decision 6 — Existing Role-Based Behavior Is the Compatibility Baseline

The 22 role-referencing unit spec files, 12 role-referencing e2e files, and
`platform-roles.spec.ts` must pass unmodified throughout M36's
implementation. They are the regression baseline this decision's parity
proof (Decision 15) is measured against, not files to be edited to
accommodate the new mechanism.

## Decision 7 — `RolesGuard` Remains the Sole Runtime Authorization Authority

`RolesGuard` (`apps/api/src/identity/roles.guard.ts`) is not modified,
wrapped, or altered in any way by this decision's authorized scope, and
remains the only mechanism that decides any request's authorization
outcome throughout M36 and after its completion. `CapabilityGuard`
(Decision 14) is implemented and unit-tested but is registered on zero
controllers — it never appears in any `@UseGuards(...)` list for any real
route during M36.

## Decision 8 — No Capability Enforcement Activation in M36

M36 activates nothing at runtime. No environment flag, feature toggle, or
conditional code path causes `CapabilityGuard`'s decision to affect any
response during M36. Enforcement activation is explicitly and permanently
assigned to a future milestone (Decision 19).

## Decision 9 — No Currently Authorized or Forbidden Outcome May Change

For every one of the 73 endpoints in Appendix A, the set of roles currently
permitted and the set of roles currently forbidden remain byte-identical
before and after M36's implementation. This is the measurable heart of
M36's safety guarantee and is directly tested by Decision 15's parity
suite.

## Decision 10 — Canonical Capability Naming Convention

Capabilities use a hierarchical `resource:action` convention, extended to
`resource:subresource:action` where a route addresses a sub-resource of a
larger domain object (e.g., an employee's certifications, or a specific
lifecycle sub-action). Examples: `positions:create`, `employees:skills:read`,
`intelligence:vacancy-risk:read`. This matches `directives/10`'s own
stated `resource:action` pattern and the existing `Permission.resource`/
`Permission.action` schema columns exactly.

**Binding split rule (how a capability key maps into the existing two
Prisma columns):** the final colon-delimited segment of a capability key is
stored as `Permission.action`; everything preceding the final colon is
stored as `Permission.resource`. This rule is fixed and must be applied
identically to every capability key, regardless of how many colon-
delimited segments it contains:

```text
employees:read              → resource "employees",           action "read"
employees:skills:read       → resource "employees:skills",    action "read"
roles:assignable:read       → resource "roles:assignable",    action "read"
```

Both resulting values remain well within `Permission.resource`'s and
`Permission.action`'s existing `VARCHAR(100)` limits for every one of the
62 unique capability keys in Appendix A — the longest resource value
produced by this rule (`employee-certifications:expiring`) is 32
characters. Because all 62 full capability keys are already pairwise
distinct (Appendix A), and this split rule is a deterministic, injective
function of the full key, the resulting `(resource, action)` tuples remain
pairwise distinct under the existing `@@unique([resource, action])`
constraint — no schema change is required to support this convention.

## Decision 11 — Endpoint-Capability Catalog: 73 Mappings, 62 Unique Permission Rows

**Endpoint mappings and unique Permission rows are explicitly distinct
counts, and must never be conflated:**

```text
73  endpoint-capability mappings — one per protected route handler
     identified in Decision 3, per Appendix A
62  unique Permission rows — the distinct set of capability names that
     result once list-read and detail-read routes sharing one genuine
     "read" operation on the same resource are correctly mapped to the
     SAME capability name, per Appendix A's derivation
```

62 is derived, not assumed: 11 of the 15 controllers in Appendix A each
contain exactly one list-route/detail-route pair (e.g., `GET departments`
and `GET departments/:id`) that represent the same underlying read
operation on the same resource and therefore correctly share one capability
name (e.g., `departments:read`). 73 endpoint mappings minus these 11
legitimate shares yields 62 unique `Permission` rows. No other endpoint in
Appendix A shares a capability name with any other. The full derivation,
controller by controller, is in Appendix A.

`@RequireCapability(...)` is added, per Appendix A, as **method-level**
metadata to all 73 protected handler methods — including the four routes
in `users.controller.ts` and the one route in `roles.controller.ts` whose
existing `@RequireRoles(...)` is class-level. The existing class-level
`@RequireRoles(...)` decorators in those two files are preserved unchanged;
the new capability metadata is added per-method so that the parity test
(Decision 15) can compare one class-level role decision against each of
several distinct, correctly-named capability decisions cleanly.

## Decision 12 — Reserved Conditional/Service-Level Capabilities (Not Seeded, Not Parity-Tested)

The following capability names are reserved for future governance and
implementation. They are documented here so a later milestone does not
need to reinvent them, but **none is seeded, none is attached to any
`@RequireCapability(...)` metadata in M36, and none is claimed as
parity-proven by this decision**, because no current route-level check can
distinguish the semantic action they name from the coarser route-level
capability that already covers their endpoint:

```text
employees:terminate
  The SEPARATED transition is one of several outcomes
  POST employees/:id/status can produce (GD-M12-1 lifecycle rules). The
  route-level capability employees:status:transition (Decision 11,
  Appendix A) covers calling this endpoint at all; distinguishing
  "terminate" specifically requires inspecting the submitted target
  status, which no route-level guard can do today.

users:deactivate
users:assign-role
  PATCH users/:id accepts firstName/lastName/email/status/roleIds, any
  subset optional. The route-level capability users:update (Decision 11,
  Appendix A) covers calling this endpoint at all; distinguishing a
  status-deactivation or a role-assignment specifically requires
  inspecting which fields the payload actually included — exactly the
  work the existing FORBIDDEN_ROLE_ASSIGNMENT and LAST_SYSTEM_ADMINISTRATOR
  service-layer guards (users.service.ts) already do for their own narrow
  purposes.

offers:rescind
  No current endpoint performs a rescind operation distinct from
  POST offers/:id/withdraw, which is itself fully route-level enforceable
  and is seeded in Appendix A as offers:withdraw. offers:rescind remains
  reserved and unattached to any endpoint until a genuinely distinct
  rescind operation exists.
```

A candidate for the same treatment, flagged for audit during
implementation but not resolved by this decision: `POST
applications/:id/advance` accepts an explicit `targetStatus` (GD-M17-1)
and may exhibit the same one-route/multiple-semantic-outcomes pattern.
Appendix A seeds it as the single route-level capability
`applications:advance`; whether any finer reserved name is warranted is an
implementation-time audit item, not a decision made here.

## Decision 13 — `PermissionsService` Design

A new `PermissionsService`, injectable alongside the existing identity
providers, exposes `resolve(roleNames: string[]): Set<string>` — a pure
function computing the **union** of every named role's mapped capabilities
via the seeded `RolePermission` table. It performs no side effects, no
caching, and no JWT interaction. It must:

```text
Return the union of all capabilities across every role name provided,
  matching RolesGuard's own .some(...) union semantics exactly
Silently ignore any role name matching no seeded Role (unknown-role
  input) — contribute zero capabilities for it, never throw
Return an empty set for a role with zero seeded RolePermission rows
  (missing-permission case) — never throw
Return an empty set for an empty input array
```

## Decision 14 — `@RequireCapability(...)` and `CapabilityGuard`

`@RequireCapability(...)` is a decorator structurally identical to
`@RequireRoles(...)` (same `Reflector`/`SetMetadata` pattern, its own
metadata key). `CapabilityGuard` is structurally identical to `RolesGuard`:
given required capabilities from metadata and a resolved capability set
from `PermissionsService`, it returns whether the required set intersects
the resolved set, with the same no-op-when-no-metadata behavior
`RolesGuard` already has. Per Decision 7, `CapabilityGuard` is implemented
and unit-tested in isolation but is never added to any controller's
`@UseGuards(...)` list during M36.

**Fail-closed requirement:** if `PermissionsService.resolve()` throws, or
returns `null`/`undefined`, `CapabilityGuard.canActivate()` must return
`false`. This is proven by a dedicated unit test with a mocked throwing
resolver, even though the guard is never runtime-registered in M36 — its
own correctness must be proven before any future milestone is trusted to
attach it.

## Decision 15 — Deterministic Parity-Proof Design

Parity is proven entirely through unit tests reading **real decorator
metadata off the real controller classes** — never through two
hand-written, independently-maintained arrays compared against each other.
The test suite imports each of the 15 controller classes listed in
Appendix A and uses `Reflect.getMetadata(ROLES_KEY, ...)` /
`Reflect.getMetadata(CAPABILITY_KEY, ...)` (via `Reflector`'s own
`getAllAndOverride([handler, class])` semantics, so class-level decorators
resolve correctly) to read each handler's actual required roles and actual
required capabilities. For each of the 73 endpoints and every non-empty
subset of the seven platform roles (127 subsets), the suite computes
`RolesGuard`'s real decision and `CapabilityGuard`'s real decision from
that metadata and asserts equality. This reuses the exact reflection-based
assertion pattern already proven in this repository's own
`roles.guard.spec.ts`, `interview.controller.spec.ts`, and
`offer.controller.spec.ts`.

## Decision 16 — Validation Gate

M36's implementation is not considered complete until every item below is
satisfied. This gate is the authoritative completion definition for any
future implementation task operating under this decision's scope:

```text
[ ] Parity proven across all 73 protected endpoints (Appendix A)
[ ] Parity proven across all 127 non-empty subsets of the seven legacy
    roles — 73 × 127 = 9,271 endpoint/subset comparisons, zero mismatches
[ ] Empty-role behavior proven (roles: [] denied on every protected
    endpoint; no-op preserved where no metadata exists)
[ ] Unknown-role behavior proven (a role name matching no seeded Role
    contributes zero capabilities, never throws)
[ ] Missing-role-permission behavior proven (a role with zero seeded
    RolePermission rows resolves to an empty set, never throws)
[ ] Resolver-failure behavior proven (PermissionsService throwing or
    returning null/undefined is handled)
[ ] Fail-closed CapabilityGuard behavior proven under all failure modes
    above
[ ] Multi-role capability-union behavior proven (a multi-role user's
    resolved capabilities equal the union across all assigned roles)
[ ] Seed idempotency proven (seed runs twice, identical resulting
    Permission/RolePermission row counts and content)
[ ] Existing PII restrictions unchanged and re-verified (RBAC-952,
    GD-M31-1/GD-M32-1/GD-M33-1 aggregate-only guarantees untouched)
[ ] Tenant isolation unchanged and re-verified (no capability lookup
    accepts or requires a caller-supplied tenantId)
[ ] LAST_SYSTEM_ADMINISTRATOR protection unchanged and re-verified
    (existing users.service.spec.ts tests pass unmodified)
[ ] FORBIDDEN_ROLE_ASSIGNMENT protection unchanged and re-verified (same)
[ ] All existing unit and e2e tests pass unmodified (22 + 12 role-
    referencing spec/e2e files, plus platform-roles.spec.ts, plus every

[ ] Type-check, lint, build, and CI succeed on the implementation commit
[ ] Metadata-drift check (Decision 17) is itself present and passing
```

## Decision 17 — Permanent Metadata-Drift Requirement (Effective Until M46 Cutover)

From the moment M36 is implemented until M46 retires role-name guards,
automated CI-enforced checks must guarantee:

```text
Every endpoint carrying @RequireRoles(...) also carries
  @RequireCapability(...) metadata — no protected endpoint may exist with
  role metadata but no capability metadata
No protected endpoint is missing from the parity-comparison map (Decision
  15) — a route added or changed without updating that map fails CI
No endpoint-capability mapping may silently change what a currently
  authorized or forbidden role can do — any change to Appendix A's mapping
  requires its own governance decision, not a routine code change
Capability metadata and legacy-role metadata must remain in lockstep —
  a change to one without a corresponding, deliberate change to the other
  fails the parity suite and therefore fails CI
```

This is a standing obligation on every future pull request touching any of
the 15 controller files in Appendix A, not a one-time M36 deliverable.

## Decision 18 — JWT and Freshness Boundary

M36 does not change the JWT contract in any way. No `capabilities` claim,
no `permissionsVersion` claim, and no other field is added to
`JwtPayload`/`RequestUser`. The existing one-hour (`JWT_ACCESS_EXPIRES_IN_SECONDS
= 3600`) role-staleness window — a role or permission change taking up to
an hour to take effect on an already-issued token, since no refresh or
revocation mechanism exists — is documented here as a **known current
limitation of the existing system**, not as a property M36 endorses or
extends as target design.

Whichever future milestone activates capability-based enforcement
(Decision 19 assigns this to M46 by default) must, in its own governance
decision, separately resolve: current-state database resolution versus
caching, an authorization-version check, cache invalidation strategy,
revocation timing, and — regardless of which approach is chosen —
**fail-closed behavior** whenever the freshness mechanism cannot produce a
definitive answer. M36 does not decide this because M36 activates no
runtime enforcement for the question to attach to; this decision names the
requirement explicitly so it cannot be silently skipped when that future
decision is drafted.
