# Background

## Why This Decision Exists

The project owner has approved a multi-year direction: collapse the current
seven role-gated experiences into one sign-in experience and one unified
Workforce Command Center, built on two human authority profiles plus
temporary administrator elevation, evidence-based decision packets, tiered
human approval, and — eventually, under separate future governance — bounded
AI assistance. This is a substantial redesign of the platform's
authorization model and its first-ever venture into AI-assisted
recommendation. Per `CLAUDE.md`'s approval-gated-changes rule, a change of
this magnitude to the authorization model and to future AI/safety posture
requires governance before implementation — and per the Anti-Drift Rule,
the highest-value next step is closing the gap between the current,
role-string-only RBAC model and the target capability-based model, not
building UI ahead of that foundation.

## What Repository Evidence Confirms

Three things independently confirm this redesign is an extension of
existing design intent, not a foreign concept:

1. `spec/11_ai_architecture.md`'s AI-001 through AI-005 already state "AI
   assists humans, does not replace them," "advisory only," and "human
   approval required for all workforce actions" — written before any
   intelligence code existed, and consistent with the proposed AI/HIL
   boundary without requiring any change to those principles.
2. The Prisma schema already contains `Permission` and `RolePermission`
   tables, exactly matching `directives/10`'s `resource:action` permission
   pattern — dormant, unseeded, and unqueried, but present since early in
   the project's history and explicitly flagged in code comments as the
   intended future state.
3. Every Phase 4 governance decision has enforced strict, repeatedly
   restated discipline against AI recommendations, alerts, autonomous
   action, and any LLM call. That discipline is this decision's foundation,
   not its obstacle — every new capability under the redesign must clear
   its own governance decision, exactly as every existing capability has.

## What Repository Evidence Also Confirms Is Missing or in Conflict

- No `DecisionCase`, `ApprovalRequest`, `ApprovalDecision`, `AgentRun`,
  `ActionExecution`, `VerificationResult`, or `ElevationSession` entity
  exists anywhere in the schema.
- No step-up authentication or elevation mechanism exists; the current
  `RBAC-1000`/`RBAC-1001` Emergency Access Rules are directive-only.
- The audit subsystem is write-only with silently swallowed write
  failures and no read endpoint of any kind — insufficient to support an
  oversight profile whose entire purpose is reviewing what happened.
- The recruiting hire endpoint's implemented RBAC (`System Administrator`,
  `HR Director`) conflicts with `directives/10` RBAC-701 ("Hiring Manager,
  HR Director") — a pre-existing inconsistency this redesign inherits and
  must resolve, not one it introduces.
- FR-850 (Global Search) is a specified, unimplemented requirement,
  independent of this redesign, that the Command Center's first release
  can and should satisfy.

# Decisions

## Decision 1 — Scope Boundary: Blueprint and Governance Only

M35 authorizes the production of governance and design documentation only.
It does not authorize, and must not be cited as authorizing, any of the
following: application source code, Prisma schema changes, database
migrations, seed data, test changes, frontend or backend implementation,
UI components, or runtime AI/LLM integration of any kind. M35's own
completion is measured by the existence and approval of its documentation
deliverables (this decision and the companion blueprint document), not by
any running system behavior. No future milestone may treat GD-M35-1 as
having authorized code merely because that code would be "consistent with"
this decision's design — every implementation milestone listed in Decision
15 requires its own governance decision before any code is written, per
the same discipline `GD-M30-1` through `GD-M34-2` already established.

---

## Decision 2 — Target Operating Model: One Sign-In Experience, One Unified Command Center

The target operating model replaces the current seven separately
role-gated experiences (System Administrator, HR Director, Workforce
Planner, Recruiter, Hiring Manager, Compliance Officer, Executive User)
with a single sign-in experience and a single unified Workforce Command
Center surface. The existing Dashboard, Intelligence, Workforce,
Recruiting, and Admin shells remain the deterministic operational and
execution layer beneath the Command Center — they are not replaced, and
approved actions continue to execute through them (see Decision 11). The
Command Center is the new decision-facing surface; it is additive to, not
a replacement of, the platform's existing operational surfaces.

---

## Decision 3 — Two Human Authority Profiles

Two human authority profiles are established as the target model's primary
identities:

```text
Workforce Decision Owner
  The primary daily operator profile. Prepares, reviews, and approves
  routine and maker-checker-tier decisions (see Decision 12). Composed
  from capability groupings drawn from the current HR Director, Workforce
  Planner, Recruiter, and Hiring Manager roles' capabilities — the exact
  composition is a capability-matrix-drafting task for the blueprint
  document, not fixed by this decision.

Independent Oversight Reviewer
  The compliance/oversight and elevated-risk second-approval profile.
  Reviews compliance findings and exceptions, high-risk decision packets,
  privileged/elevation activity, approval/execution/verification history,
  aggregate executive-risk information, and tenant-scoped audit history.
  Approves only the elevated-risk action list in Decision 13 — never
  routine Workforce Decision Owner actions. This profile's capability
  grant must be purpose-built, not composed as the union of the current
  Compliance Officer and Executive User roles' access (see Decision 10 and
  the blueprint document's capability matrix).
```

Neither profile is activated for real production users by this decision.
Their formal capability grants are drafted in the blueprint document and
implemented no earlier than M36 (authorization foundation) and M39 (audit
prerequisite, required before Independent Oversight Reviewer activation —
see Decision 9).

---

## Decision 4 — Temporary System Administrator Elevation

A permanent, standing System Administrator persona is replaced in the
target model by temporary, reason-logged, time-boxed, step-up-authenticated
elevation sessions. The elevation model (fields, approval requirement, and
expiry behavior) is specified in the blueprint document. This decision
authorizes the *design* of that model only. Elevation may be *built*
(M37) before the audit prerequisite (M39) is complete, but it must not be
*activated for production use* until M39 is operational — an elevation
mechanism without a working audit trail would be a net new risk, not a
safety improvement, over today's permanent SA fixture.

Temporary elevation does not grant, and must never be designed to grant,
blanket employee or candidate PII access. Any elevation request that
genuinely requires PII-scoped access must be independently justified,
narrowly scoped to only the specific records required, and remains fully
subject to the case-scoped, PII-minimized evidence-access principle
established in Decision 10 — elevation is never a mechanism for bypassing
that principle.

---

## Decision 5 — Seven Legacy Roles: Retained During Migration, Retirement Gated on Proven Capability Parity

All seven current platform roles (System Administrator, HR Director,
Workforce Planner, Recruiter, Hiring Manager, Compliance Officer,
Executive User) remain assignable to real production users throughout the
migration. This is a deliberate, evidence-based decision: the seven role
names are load-bearing across every recruiting controller
(`application.controller.ts`, `candidate.controller.ts`,
`hire.controller.ts`, `interview.controller.ts`, `offer.controller.ts`),
every workforce and intelligence endpoint, and at least 22 backend unit
spec files plus 12 backend e2e spec files. Retiring them immediately would
be an uncontrolled, high-blast-radius change inconsistent with this
project's incremental-and-reversible governance discipline.

Direct production assignment of the seven legacy role names may be retired
**only after** a capability-parity proof demonstrates that the new
permission-based authorization model (M36) produces identical HTTP
authorization outcomes to the current role-string model, for every
existing endpoint, for every one of the seven roles. Until that proof
exists and is reviewed, the seven roles remain the only assignable
identities. After retirement, the seven role names are preserved
permanently as (a) capability-grouping vocabulary inside the new
permission model, and (b) the regression/compatibility test baseline
proving the new model behaves identically to the old one.

---

## Decision 6 — AI Job Functions: Logical Responsibilities, Not Autonomous Agents

The seven proposed AI job functions (Executive Briefing Agent, HR
Operations Agent, Workforce Intelligence Agent, Talent Pipeline Agent,
Selection Support Agent, Policy Guard Agent, Platform Operations Agent) are
established as **logical responsibilities inside the existing NestJS
`IntelligenceModule`** — not as seven independently authenticated,
separately deployed, or separately identitied autonomous agents. No AI job
function receives a `User` row, a password, a JWT, or a login session of
any kind, under this decision or any milestone it authorizes. Where an
AI-prepared action needs an actor reference for audit purposes, it must
use a `service_actor`-type reference analogous to the existing
`SYSTEM_USER_ID` audit sentinel already established in `AuditService`
(`apps/api/src/audit/audit.service.ts`) — extended, not replaced, by any
future decision. Separate service identities or independently deployed
agent runtimes may be evaluated in a future, separately governed decision
only if genuine asynchronous agent execution needs justify that added
complexity; this decision does not pre-authorize that evolution.

---

## Decision 7 — LLM/Runtime AI Remains Prohibited Until a Later Dedicated Governance Decision

`GD-M30-1` Decision 12, `GD-M32-1` Decision 12, `GD-M33-1` Decision 12, and
`GD-M34-1` Decision 19 — each prohibiting any OpenAI/LLM/external AI
provider call under any circumstance — remain in full, unamended force.
This decision does not relax, narrow, or supersede any of them. No LLM
call, prompt execution, or AI-provider-generated text may exist anywhere
in the platform as a result of this decision or any milestone through M43
in the roadmap (Decision 15). The first-ever exception requires its own
dedicated governance decision (targeted at M44, LLM Shadow Mode) satisfying
every prerequisite `GD-M30-1` Decision 12 already lists: prompt versioning,
cost tracking, failure handling, and confirmation that core platform
operations continue if the AI provider is unavailable, per
`spec/11_ai_architecture.md`'s AI Failure Handling section.

---

## Decision 8 — Deterministic Search Is Distinct From Conversational AI Commands

Global Search, satisfying the existing, unimplemented `spec/01_requirements.md`
requirements FR-850 (Global Search), FR-851 (Workforce Search), and FR-852
(Report Search — "access controlled by permissions"), is authorized as a
**fully deterministic, permission-filtered, tenant-scoped** capability, with
no AI or LLM involvement of any kind. It must be labeled and presented as
**Search**, not as an "AI command bar" or any similarly branded conversational
interface. Conversational AI commands and natural-language action initiation
are explicitly deferred beyond the roadmap in Decision 15 and require their
own future governance decision; they are never authorized as bypassing
policy evaluation, authorization, required human approval, deterministic
execution, or audit, regardless of when or how they are eventually
introduced. This decision does not narrow or supersede `GD-M34-2` Decision 7's
prohibition on alerts, watchlists, and recommendation cards — Search is
retrieval, not recommendation, and remains outside that prohibition's
scope precisely because it recommends nothing.

---

## Decision 9 — Audit Prerequisite Required Before Independent Oversight Reviewer Activation

The current `AuditService.logEvent()` is confirmed write-only: it wraps its
own `create()` call in a try/catch, logs any failure via `Logger.error`,
and returns normally with no retry, no dead-letter path, and no rethrow. No
`AuditController` or audit-read endpoint exists anywhere in the repository.
This is insufficient to support a profile whose defining purpose is
reviewing what happened. Accordingly:

```text
Independent Oversight Reviewer MUST NOT be activated for any real
production user until a tenant-scoped audit-read API, a
permission-controlled audit viewer, required filtering/search, actor/
action/result/resource/timestamp visibility, approval-and-execution
correlation, tamper-detection controls, retention enforcement, and
observability/recovery for failed audit writes are all operational
(targeted at M39 in the roadmap, Decision 15).

Elevation sessions (Decision 4) are subject to the same gate: they may be
built (M37) before M39, but may not be activated for production use until
M39 is operational, for the identical reason — a privilege-granting
mechanism without a working, reviewable audit trail is a net new risk.
```

The full specification of this prerequisite is the responsibility of the
companion blueprint document.

---

## Decision 10 — Case-Scoped, PII-Minimized Evidence Access

Any evidence surfaced inside a decision packet or to the Independent
Oversight Reviewer must be scoped to the specific case under review and
must minimize or mask personally identifiable information by default,
unless the specific review genuinely requires unmasked access. This
principle extends, rather than contradicts, the individual-level-data
prohibitions already established in `GD-M32-1` Decision 11 and `GD-M33-1`
Decision 6/7/11 for the existing aggregate-only Intelligence signals: those
existing endpoints' aggregate-only guarantees are unchanged by this
decision. Decision-packet evidence is a new, separately governed exposure
surface (because it is inherently row-level, unlike the existing
Intelligence signals) and must declare its own case-scoping and masking
rules in the blueprint document and in a future implementation-stage
governance decision (targeted at M38) — it is not automatically covered by
extending an existing aggregate-only guarantee.

---

## Decision 11 — No Autonomous AI Execution; Human Approval Required for Consequential Actions

No AI job function, under this decision or any future decision this
document's roadmap contemplates, may execute a consequential workforce
action. Every `ActionExecution` (a future entity defined by the blueprint
document) must trace to a human `ApprovalDecision` with status `APPROVED`,
and must call only the platform's existing deterministic service layer
(the same Workforce/Recruiting/Admin endpoints that already enforce their
own RBAC today) — never a new, parallel, AI-triggered write path. This
restates and extends, without weakening, AI-001 ("AI assists humans; AI
does not replace humans"), AI-004 ("AI recommendations are advisory
only"), and AI-005 ("human approval is required for all workforce
actions") from `spec/11_ai_architecture.md`, and the AI Constraints
section's prohibition on autonomous hiring, scheduling, policy, and
compliance actions.

---

## Decision 12 — Tiered Approval Model (Three Distinct Tiers)

Human approval for consequential decisions is tiered. The three tiers are
distinct concepts and must never be conflated with one another in any
future design, endpoint, or UI element:

```text
Tier 1 — Routine, single-human approval
  Applies to: candidate movement, drafting, analysis, scenario
  preparation, information requests, and other routine AI-supported
  actions. Requires exactly one authorized human decision. No second
  approver of any kind.

Tier 2 — Workforce Decision Owner maker-checker approval
  Applies to: routine final offer authorization and routine hire
  authorization. Requires two distinct humans, BOTH drawn from the
  Workforce Decision Owner population:
    one department/hiring authority
    one HR authority
  This is an operational separation-of-duties control WITHIN the
  Workforce Decision Owner profile. It is NOT Independent Oversight
  Reviewer involvement, and the Reviewer is not a participant in this
  tier by default.

Tier 3 — Independent Oversight Reviewer approval
  Applies ONLY when a case triggers one of the elevated-risk conditions
  enumerated in Decision 13. The Reviewer is never a standing participant
  in routine hiring or routine Tier 1/Tier 2 actions — only cases that
  independently trigger a Decision 13 condition escalate to this tier.
```

Tier 2 and Tier 3 are related but not interchangeable: a two-person check
is not, by itself, evidence that Independent Oversight Reviewer approval
occurred, and a case must not be miscategorized as satisfying Tier 3 merely
because two humans were involved in it.

---

## Decision 13 — Independent Oversight Reviewer Approval Triggers, and the Hire-Endpoint RBAC Inconsistency

Independent Oversight Reviewer approval (Tier 3) is required only when a
case triggers one or more of the following elevated-risk conditions:

```text
Compliance exceptions
Failed-control override attempts
Privileged or emergency access requests
Authorization, policy, or security-configuration changes
Workforce-plan or forecast activation where the approver also prepared it
  (self-review)
Sensitive bulk actions (bulk hiring, rejection, separation, or access
  changes)
Any other condition the blueprint document or a future governance
  decision explicitly defines as elevated-risk
```

**Confirmed inconsistency requiring future resolution:** the implemented
hire endpoint (`apps/api/src/recruiting/hire.controller.ts`, line 57)
enforces `@RequireRoles('System Administrator', 'HR Director')`, per
`GD-M19-1`. `directives/10_role_based_access_rules.md` RBAC-701 states
"Hiring approval requires: Hiring Manager, HR Director" — a different role
set, and one that does not include System Administrator. This decision
does not resolve this inconsistency and does not amend `GD-M19-1` or
`directives/10`. It records the inconsistency as a known, pre-existing
defect that the target Tier 2 maker-checker model (department/hiring
authority + HR authority) is expected to resolve, and assigns that
resolution to a future implementation milestone (M40, per Decision 15). No
change to the hire endpoint's current RBAC behavior occurs as a result of
this decision.

## Decision 15 — Post-M35 Implementation Roadmap

The following milestone sequence is authorized as the roadmap this
decision's blueprint work plans toward. Authorization of this sequence is
a planning record only — **each milestone requires its own separate
governance decision before any of its implementation work begins**, per
Decision 1:

```text
M36 — Capability-Based Authorization Foundation
  Seed real Permission/RolePermission rows; introduce PermissionsGuard
  running in parallel with RolesGuard, no live-endpoint behavior change;
  prove capability parity against all existing role-dependent tests.

M37 — Elevation Sessions (build, not production activation)
  ElevationSession entity, step-up auth, dual-party approval logic for
  elevation requests. May be built before M39, but not activated for
  production use until M39 is operational (Decision 9).

M38 — Decision Case and Approval Foundation
  DecisionCase, EvidenceItem, PolicyEvaluation, ApprovalRequest,
  ApprovalDecision, VerificationResult entities; three-tier approval
  logic (Decision 12) implemented and tested; fully deterministic, zero
  AI involvement.

M39 — Audit Prerequisite (Read API + Viewer)
  Tenant-scoped audit-read API, permission-controlled viewer, filtering,
  tamper-detection, retention enforcement, and failure-recovery design
  for AuditService. Required before Independent Oversight Reviewer
  activation and before elevation (M37) is activated for production use.

M40 — Hire-Endpoint Maker-Checker Resolution
  Resolves the Decision 13 RBAC inconsistency by implementing Tier 2
  maker-checker (department/hiring authority + HR authority) on the hire
  flow, superseding GD-M19-1's SA/HRD-only gate under the new capability
  model via its own governance decision.

M41 — Deterministic Global Search
  Permission-filtered, tenant-scoped Search satisfying FR-850/851/852.
  No AI. Implemented before or alongside the first Command Center
  release, not after it.

M42 — Deterministic Policy Guard Logical Function
  The Policy Guard responsibility implemented as a rules-evaluator inside
  the existing Intelligence module. Zero LLM calls.

M43 — Deterministic Command Center MVP
  The first Command Center release: deterministic Search (M41), decision
  cases and approvals (M38) with all three tiers correctly routed,
  oversight surfaces for Independent Oversight Reviewer (gated on M39),
  and audit visibility (M39). No LLM component of any kind is present in
  this milestone.

M44 — LLM Shadow Mode (Read-Only)
  Only after M43 ships. Strictly read-only/shadow — output is logged and
  reviewed, never shown to end users as actionable, never feeding
  execution. Requires its own dedicated governance decision (Decision 7).

M45 — Governed Runtime LLM Integration (Narrow)
  Only after M44's shadow-mode results are reviewed and a separate
  governance decision explicitly authorizes runtime use, scoped to
  preparation/summarization functions only. Conversational AI commands
  remain deferred beyond this milestone, requiring their own future
  decision.

M46 — Two-Profile Cutover
  Migrate real user assignments from the seven legacy roles to the two
  authority profiles, gated on the M36 capability-parity proof. Legacy
  roles retained permanently as fixtures/capability groupings (Decision
  5).
```
